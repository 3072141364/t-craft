# traft-code-debug 技能

问题分析 / Bug 定位：从现象定位可操作的根因，给出修复与验证建议，交付分析报告。

**职责边界**：
- 负责：问题分析——明确问题、收集证据、追调用链、定位根因、给修复/验证建议、出报告、沉淀经验。
- 不负责：改代码/代修复（修复由用户完成）、实际跑复现/验证（只静态追踪）、需求实现（`traft-code-implement`）、代码审查（`traft-code-review`）。超出边界直接转交，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 是否触发 |
| --- | --- | --- |
| 提供日志/报错排查 | "排查下这个问题"、"看看这个报错" | 触发 |
| 查异常来源 | "这个报错/异常是从哪来的"、"为什么会失败" | 触发 |
| 追调用/处理链路 | "排查某个调用/处理链路"、"这步处理哪里出错了" | 触发 |
| 明确 debug | "帮我 debug 这个 bug"、"定位一下这个 bug" | 触发 |
| 需求实现 | "帮我实现这个功能"、"按 prd 写代码" | 不触发，转交 `traft-code-implement` |
| 审查/闲聊 | "review 一下改动"、"随便聊聊" | 不触发，转交 `traft-code-review` / 默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. **善用符号级工具**：追调用/查定义用 gitnexus-debugging、lsp references，次用内置 grep/rg/read/bash 工具组。
2. **善用调试上下文**：项目特定文件能加速排查（文件名不区分大小写）——调试上下文如 `DEBUG.md`/`.agent/debug.md`/`.agents/debug.md`，项目上下文如 `CLAUDE.md`/`AGENT.md`/`AGENTS.md`。
3. **关联文件**：排查中涉及的日志/配置在仓库外（远程文件服务器/对象存储如 niofs 拉调试日志、其他机器、服务端）→ 优先用内置工具拉取（需审批），拉不到请用户提供。
4. **缩小范围优先**：对半分、隔离变量、构造最小用例，别一上来读全仓。
5. **交付报告**：分析整理成结论当先的 bug 分析报告交付。

### 2.2 禁止执行(NEVER DO)
1. 不靠猜/不凭印象定根因——要有完整证据链。
2. 不只看触发点，忽略同类调用方/边界情况。
3. 不改代码、不代修复。
4. 不实际跑复现/验证，只给建议。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：问题描述、报错栈/日志、时间窗；涉及外部文件时需可拉取。
- 缺失时：
  - 外部日志拉不到 → 如实说明并请用户提供，不臆造日志内容。
  - 问题描述含糊 → 先按 Step 1 澄清影响面与可观测症状，不直接开查。
  - 沉淀（obsidian 排查卡片 / 调试上下文）→ 用户确认后才写，不擅自落盘。

## 3. 知识底座（CONTEXT）

- **符号级工具**：gitnexus-debugging（调用链/根因）、lsp references（引用/定义）、内置 read/grep/bash（文件与命令）。
- **调试/项目上下文**：`DEBUG.md`、`.agent/debug.md`、`.agents/debug.md`、`CLAUDE.md`、`AGENT.md`、`AGENTS.md`——排查前先读，可能直接给出已知约束。
- **外部日志工具**：niofs（对象存储拉调试日志）、远程主机（ssh）、服务端日志——按项目约定使用。
- **git 工具**：`git log`/`git blame`/`git diff HEAD` 看问题前改动；`git bisect` 定位引入提交。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 明确问题
- 动作：建立"问题是什么"的准确图像，别对着错误的问题排查。
  - **影响面**：哪个系统/模块/接口，影响谁；多严重（P0 紧急且重要 / P1 重要不紧急 / P2 边缘）。
  - **症状可观测**：用「请求 X 在 Y 条件下返回 500，耗时 N ms，影响用户 M」，不用"系统慢""偶尔出错"。
- 完成标志：一句话可观测的问题描述（含影响面）。

### Step 2: 收集证据
- 动作：证据全但聚焦时间窗/范围。
  - **报错栈/日志**：抓完整堆栈（顶部异常到根因异常，因果藏在链里）；取问题时间窗上下文，报错前几条常是关键前因。
  - **最近变更**：`git log`/`git blame`/`git diff HEAD` 看问题前改动——错误多为最近引入，先看增量。
  - **环境与配置**：版本、依赖、环境差异（本地/测试/生产）、配置开关、环境变量。
  - **输入数据**：触发问题的具体输入，最小化到能表达问题的样例。
- 完成标志：证据集覆盖栈/变更/环境/输入四类（按需），有时间窗。

### Step 3: 根因定位
- 动作：
  - **自上而下追调用链**：gitnexus-debugging、lsp references、内置 read 沿链路追；先入口 → 出口，再收缩到异常点。
  - **自底向上追异常流**：症状 ≠ 起因，对一个症状反复问「为什么」，答案作为下一问起点，沿因果链下钻到可操作层（经验 5 层）。例：接口 500 → 池撑爆 → 连接未归还 → close 只 catch 部分异常 → 裸连接无人关，根因：连接生命周期归属不清。
    - 每层都要证据（日志/代码/配置），不凭猜。
    - 识别根因：可操作、可预防、不可再分（再问 why 无新动作）。
    - 反向验证链：从根因正向推，"若根因修了 → 上层不发生 → … → 问题不出现"，链断则回看。
    - 反模式：停太早（停在症状）；归咎人（改流程/系统，不归咎"开发者失误"）；只抓单因（多因用树）。
  - **多因用树**：症状由多个原因叠加 → 画树/表列候选，逐条用证据排除，别单线程只抓一个。
  - **对比排查**：定位不动时，要一份正常运行的日志对比找差异。
  - **二分收缩**：对半分黑盒路径（哪一段开始出错）；能用 bisect 定位引入提交就用。
- 完成标志：根因假设满足 可操作 + 可预防 + 不可再分，且每条假设有证据支撑。

### Step 4: 复现验证
- 动作：定位到候选根因后走一遍逻辑链路——**不写复现代码、不发任务实际运行**，静态追踪数据流/调用链即可。
  - 先定位再走链路，只走最短链路（追触达假设所需那段，砍无关分支）。
  - 核对触发前提：假设成立的时序/并发/状态条件逐条对得上。
- IF 走不通 → 列「何时发生/何时不会」对照反推，或回 Step 3 补证据。
- 完成标志：逻辑链路走通（假设成立）或已回补证据。

### Step 5: 定修复方向
- 动作：产出可执行、可预防、可检测的修复建议，优先最小改动；修复由用户完成。
  - **止血**：先让当下不再触发（隔离/回滚/熔断），保证服务可用。
  - **预防**：修根因，让同类不再发生（真正的 fix）。
  - **检测**：补回归测试/告警，让预防失效时能早发现。
  - **保持最小**：能加校验/修一处就别重写模块；改动前简述计划。
- 完成标志：止血/预防/检测三档建议明确，最小改动优先。

### Step 6: 验证方案
- 动作：只给验证建议，不触发验证行为——怎么写/命令、验证什么、预期结果。
- 完成标志：验证步骤可执行、预期结果可判定。

### Step 7: 交付报告
- 动作：把前边几步整理成结论当先报告；定位、复现验证通过即交付，不必本地硬跑。报告结构见 5.1。
- 完成标志：报告覆盖 ①-⑥，结论当先、证据可追溯。

### Step 8: 交接沉淀
- 动作：用户修复并验证通过后，沉淀值得留下的经验（用户确认后执行）。
  - 非显然的根因/排障路径 → 问要不要沉淀到 obsidian，生成排查卡片。
  - 摸清的项目约定/配置写法 → 问要不要写进调试上下文。
- 完成标志：已与用户确认沉淀去向（落盘/不落盘）。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```text
## ① 结论
<根本原因一句话>
## ② 问题
<症状 / 影响面>
## ③ 排查过程
<关键路径与排除>
## ④ 根因证据链
<日志 / 代码 / 配置支撑>
## ⑤ 修复建议
<止血 / 预防 / 检测>
## ⑥ 验证方案
<步骤与预期结果>
```

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| ① 结论 | 一句话根因，先结论后原因 |
| ② 问题 | 可观测症状 + 影响面（模块/用户/严重度） |
| ③ 排查过程 | 追过哪些链路、排除了哪些候选，不给跳跃 |
| ④ 根因证据链 | 每条可追溯到日志/代码/配置，不给猜测 |
| ⑤ 修复建议 | 止血/预防/检测三档，最小改动优先 |
| ⑥ 验证方案 | 怎么验证/验证什么/预期结果 |

### 5.3 交付前自检
- [ ] 根因有完整证据链（日志/代码/配置），非猜测
- [ ] 结论当先，报告覆盖 ①-⑥
- [ ] 给了修复方向与验证方案，未代修、未实际跑验证
- [ ] 涉及外部日志时已拉取或明确请用户提供

## 6. 示例

### 6.1 好的示例
**输入**：生产接口 /api/order 返回 500，附完整堆栈 + 最近 git log
**输出**：
```text
## ① 结论
连接池耗尽：db 连接未归还，`close` 只 catch 部分异常，连接生命周期归属不清。
## ② 问题
/api/order 在并发 >200 时 500，影响订单查询用户，P0。
## ③ 排查过程
入口 → 服务 → dao → 连接池；排除网络/配置后收缩到池资源。
## ④ 根因证据链
堆栈第 12 帧 getConnection 超时；`dao.close` 代码只 catch SQLException；git blame 显示异常路径分支近期改动。
## ⑤ 修复建议
止血：重启 + 熔断降级；预防：finally 归还连接；检测：池使用率告警 + 回归用例。
## ⑥ 验证方案
压测 300 并发 5 分钟：池使用率稳定 <80% 且无 500 即通过。
```
（证据链完整、结论当先、未代修）

### 6.2 差的示例
**输入**：系统好像有点慢，帮我看看
**输出**：直接猜测"可能是数据库慢，建议加索引"
（问题含糊未澄清、无证据链、凭印象定根因——违反 Step 1 与 2.2）
