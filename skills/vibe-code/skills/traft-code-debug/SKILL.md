# traft-code-debug 问题分析 / Bug 定位

拿到一个问题,目标是:**帮用户从现象定位可操作的根因、给出修复与验证建议、生成分析报告**;不代修、不改码。

## RULES

### ALWAYS DO
- **善用符号级工具**:追调用 / 查定义用 gitnexus-debugging、lsp references, 次用agent内置grep / rg /read /bash 工具组。
- **善用调试上下文**:项目特定文件能加速排查，文件名不区分大小写。调试上下文 如`DEBUG.md` / `.agent/debug.md` / `.agents/debug.md`,项目上下文 如`CLAUDE.md` / `AGENT.md` / `AGENTS.md`。
- **关联文件**:排查中涉及的日志 / 配置若在仓库外(远程文件服务器 / 对象存储,如 niofs 拉调试日志;其他机器;服务端),优先用内置工具拉取(需审批),拉不到请用户提供。
- **缩小范围优先**:对半分、隔离变量、构造最小用例,别一上来读全仓。
- **交付报告**:把分析整理成结论当先的 bug 分析报告交付。


### NEVER DO
- 不靠猜 / 不凭印象定根因,要有完整证据链。
- 不只看触发点,忽略同类调用方 / 边界情况。
- 不改代码、不代修复;不实际跑复现 / 验证,只给建议。

## 排查流程

1. **明确问题** 先建立"问题是什么"的准确图像,别对着错误的问题排查。
   - **影响面**:哪个系统 / 模块 / 接口,影响谁;多严重(P0 紧急且重要 / P1 重要不紧急 / P2 边缘)。
   - **症状要可观测**:用「请求 X 在 Y 条件下返回 500,耗时 N ms,影响用户 M」,不用"系统慢""偶尔出错"。

2. **收集证据** 证据是定位的基础,要全但聚焦时间窗 / 范围。
   - **报错栈 / 日志**:抓完整堆栈(顶部异常到根因异常,因果藏在链里);日志取问题时间窗上下文,报错前几条常是关键前因。
   - **最近变更**:`git log` / `git blame` / `git diff HEAD` 看问题前改动;错误多为最近引入,先看增量。
   - **环境与配置**:版本、依赖、环境差异(本地 / 测试 / 生产)、配置开关、环境变量。
   - **输入数据**:触发问题的具体输入 / 数据,最小化到能表达问题的样例。

3. **根因定位**
   - **自上而下追调用链**:用 gitnexus-debugging、lsp references、内置 read 工具组沿链路追;先看入口 → 出口,再收缩到异常点。
   - **自底向上追异常流**:症状 ≠ 起因,对一个症状反复问「为什么」,答案作为下一问起点,沿因果链下钻到可操作层(经验 5 层)。例:接口 500 → 池撑爆 → 连接未归还 → close 只 catch 部分异常 → 裸连接无人关,根因:连接生命周期归属不清。
     - 对症状迭代问 why,每层都要证据(日志 / 代码 / 配置),不凭猜。
     - 识别根因:可操作、可预防、不可再分(再问 why 无新动作)。
     - 反向验证链:从根因正向推,"若根因修了 → 上层不发生 → … → 问题不出现",链断则回看。
     - 反模式:停太早(还停在症状);归咎人(改流程 / 系统,而非归咎"开发者失误");只抓单因(多因用树图)。
   - **多因用树**:症状可能由多个原因叠加,画树 / 表列出候选,逐条用证据排除,别单线程只抓一个。
   - **对比排查**:问题定位不动时,要一份正常运行的日志,对比找差异。
   - **二分收缩**:对半分黑盒路径(哪一段开始出错);能用 bisect 定位引入提交就用。

4. **复现验证** 定位到候选根因后,走一遍逻辑链路验证它——**不写复现代码、不发任务实际运行**,静态追踪数据流 / 调用链即可。逻辑走通=假设成立;走不通=回头补证据或调整假设。
   - **先定位,再走链路**:验证只服务"根因假设",别对全部问题盲目跑代码。
   - **只走最短链路**:追触达假设所需的那段,砍掉无关分支。
   - **核对触发前提**:假设成立要满足的时序 / 并发 / 状态条件,逐条对得上。
   - 走不通 → 列「何时发生 / 何时不会」对照反推,或回第 3 步补证据。

5. **定修复方向** 产出可执行、可预防、可检测的修复建议,优先给最小改动;修复由用户完成。
   - **止血**:先让当下不再触发(隔离 / 回滚 / 熔断),保证服务可用。
   - **预防**:修根因,让同类不再发生(真正的 fix)。
   - **检测**:补回归测试 / 告警,让预防失效时能早发现。
   - **保持最小**:能加校验 / 修一处就别重写模块;改动前简述计划。

6. **验证方案** 只给验证建议,不触发验证行为。
   - **怎么验证**:步骤 / 命令;
   - **验证什么**:修复后某行为不再出现;
   - **预期结果**:什么样算通过;

7. **交付报告** 把前边几步(问题 / 排查 / 根因 / 修复 / 验证)整理成结论当先报告;定位、复现验证通过即交付,不必本地硬跑。
   - **报告结构(结论当先)**:
     - ① **结论**:根本原因一句话简述;
     - ② **问题**:症状 / 影响面;
     - ③ **排查过程**:关键路径与排除;
     - ④ **根因证据链**:日志 / 代码 / 配置支撑;
     - ⑤ **修复建议**:止血 / 预防 / 检测;
     - ⑥ **验证方案**:见第 6 步建议。

8. **交接沉淀** 用户修复并验证通过后,再把值得留下的沉淀掉,避免下次重踩。
   - **沉淀经验**:非显然的根因 / 排障路径 → 问要不要沉淀到obsidian，生成排查卡片。
   - **项目约定**:摸清的项目约定 / 配置写法 → 问要不要写进调试上下文。
