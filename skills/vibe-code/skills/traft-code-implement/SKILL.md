# traft-code-implement 技能

方案实现（研发阶段③）：把已对齐的需求（prd）落成代码。**头脑风暴已经思考过了**——需求、边界、验收标准都在 prd.md，实现不再重新深挖；这里的"思考"是把方案落成具体改动规划，并暴露实现中才浮现的新问题。

**职责边界**：
- 负责：读 prd、规划改动、写码、验证、交付审核。
- 不负责：需求深挖（`traft-requirements`）、提交代码（提交由用户触发，走 `traft-code-git`）、文档落盘（`traft-code-docs`，落盘需审批）。超出边界直接转交，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 是否触发 |
| --- | --- | --- |
| 进入实现阶段 | 阶段③、prd 已对齐、开始落地 prd | 触发 |
| 写/改代码 | "帮我实现"、"按 prd 写代码"、"落地这个方案" | 触发 |
| 需求还含糊 | "头脑风暴一下"、"需求还没想清楚" | 不触发，先走 `traft-requirements` |
| 审查/排查 | "review 一下"、"排查 bug" | 不触发，转交 `traft-code-review`/`traft-code-debug` |
| 闲聊/泛泛提问 | "随便聊聊" | 不触发，交给默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. **先读 prd 再写码**：动手前读 `traft-code-docs` 落盘的 prd.md（需求 + 方案 + 验收标准）；方案不清楚或与 prd 冲突，先问，不擅自改已定的事。
2. **先思考再动手**：写码前默一遍要改哪些文件、用什么衔接点、怎么验证；有多种解读全呈现，有更简单方案 push back，说不清就停下问——不默默替用户选。
3. **简洁优先**：解决问题的最小代码；不写要求之外的功能；单次使用不抽象；不为不可能发生的场景写错误处理；写多了（200 行本可 50 行）重写。自问"资深工程师会说过度复杂吗？"
4. **外科手术式修改**：只动该动的；不顺手优化相邻代码/注释/格式；匹配既有风格；发现无关死代码**指出来**不删；移掉自己改动导致无用的 import/变量/函数。每行改动可追溯到需求。
5. **用查证与注释**：调用链/影响面走 `traft-code-intelligence`；注释遵循 `traft-code-comment`。
6. **交付审核，不代提交**：实现与验证后，把改动与结果展示给用户审核；提交由用户确认后触发（走 `traft-code-git`），本技能不提交。

### 2.2 禁止执行(NEVER DO)
1. 不重新深挖已对齐的需求（那是阶段①）；不擅自改 prd 已定的边界/验收标准。
2. 不做超出 prd 的投机功能、不加"万一以后要"的抽象。
3. 不顺手改无关代码、不删既有死代码（除非被要求）。
4. 不手动 git 提交、不自动 push。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：prd.md（需求 + 方案 + 验收标准）。
- 缺失时：prd 未落盘 → 先走 `traft-requirements` 深挖 + `traft-code-docs` 落盘，不凭口述写码。

## 3. 知识底座（CONTEXT）

- **prd 位置**：`requirements/<需求名>/prd.md`（`traft-code-docs` 落盘）。
- **查证**：`traft-code-intelligence`（调用链/影响面路由）。
- **注释**：`traft-code-comment`（非必要不注释、结构化标记）。
- **验证**：`traft-code-make`（make 目标，含 `make format` / `make lint`）。
- **提交**：`traft-code-git`（用户触发）。
- **决策落盘**：`traft-code-docs`（重要设计决策记 adr，需审批）。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 读 prd
- 动作：读 `requirements/<需求名>/prd.md` 的需求 + 方案 + 验收标准。
- 完成标志：需求/方案/验收标准都清楚；有疑问已先问。

### Step 2: 规划改动
- 动作：列改动文件/模块，说清衔接与验证方式。
- 完成标志：改动规划明确，多种解读已呈现、更简单方案已讨论。

### Step 3: 写码
- 动作：按 2.1 规则落码（简洁、外科手术；查证/注释走对应技能）。
- 完成标志：改动完成，每行可追溯到需求。

### Step 4: 验证
- 动作：跑 prd 相关测试 / make 目标（走 `traft-code-make`，含 `make format` / `make lint`）；对照验收标准。
- 完成标志：测试通过、验收标准逐条核过。

### Step 5: 交付审核
- 动作：展示改动与验证结果，等用户确认；提交由用户触发（走 `traft-code-git`）；重要设计决策记 adr（`traft-code-docs`，落盘需审批）。
- 完成标志：改动与结果已交付，用户确认；未代提交。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```text
## 改动
- <文件>：<改了什么，追溯需求点>
## 验证
- <测试/命令 + 结果>
## 验收对照
| 验收标准 | 达成 | 证据 |
|---------|------|------|
```

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| 改动 | 每项可追溯到 prd 需求点 |
| 验证 | 实际跑过的测试/make 目标与结果 |
| 验收对照 | 逐条核 prd 验收标准，证据来自实际验证 |

### 5.3 交付前自检
- [ ] 已读 prd，未擅自改已定边界
- [ ] 改动最小、外科手术式，每行可追溯
- [ ] 验证已跑（测试/make），验收对照完成
- [ ] 未提交、未 push，交付等用户审核

## 6. 示例

### 6.1 好的示例
**输入**：开始实现订单导出（阶段③）
**输出**：
```text
## 改动
- src/export/service.ts：新增导出任务入口（prd 验收 1）
- src/export/queue.ts：异步队列消费（prd 验收 2）
## 验证
- make test：42 passed；make lint：通过
## 验收对照
| 验收标准 | 达成 | 证据 |
|---------|------|------|
| 1. 筛选后导出 CSV | 达成 | export 单测通过 |
| 2. 超限分批提示 | 达成 | 边界用例通过 |
```

### 6.2 差的示例
**输入**：开始实现订单导出（阶段③）
**输出**：没读 prd 直接写；或写完顺手"优化"了相邻模块的缩进与命名；或改完直接 `git commit`。
（违反 2.1①④⑥——先读 prd、外科手术、提交由用户触发）
