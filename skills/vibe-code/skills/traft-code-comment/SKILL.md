# traft-code-comment 技能

代码注释助手：判断该不该注、怎么注、怎么打标记。服务于写注释、改注释、审注释、agent 生成代码时。

**职责边界**：
- 负责：注释的增删改审、结构化标记（TODO/FIXME 等）的规范。
- 不负责：重构/重写代码（先改名、再重构，注释是最后手段——那是 `traft-code-implement` 的事）。超出边界直接说明，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 是否触发 |
| --- | --- | --- |
| 补注释 | "帮我完善注释" | 触发 |
| 判断该不该注 | "这段代码要不要加注释" | 触发 |
| 打标记 | "写个 TODO / FIXME" | 触发 |
| 优化注释 | "优化注释" | 触发 |
| 生成代码时 | agent 写码过程中涉及注释 | 触发（内置约束） |
| 写功能/改逻辑 | "帮我实现"、"修个 bug" | 不触发，转交 `traft-code-implement`/`traft-code-debug` |
| 闲聊/泛泛提问 | "随便聊聊" | 不触发，交给默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. **非必要不注释**：先改名、再重构，注释是最后手段。函数名/类名/成员名见名知义，能靠改名说清楚的不加注释；长函数、晦涩逻辑先重构（拆函数、降耦合），重构解决不了的才注释——别拿注释给坏代码打补丁。
2. **注释写法**：格式遵循所在语言的主流规范，不跨语言混用——C++ 遵循 Google C++ Style Guide；Python 遵循 PEP 8；其他语言先对齐项目同类文件的既有注释风格，无先例再按该语言官方/主流规范写。写在要解释的代码旁，直说为什么这么写，不铺垫背景、不绕弯子。一句话能说清的不写段落；零信息量的模糊概括（"处理数据""优化性能"）写了不如不写。
3. **以下情况必须注释**（注释写代码说不出来的信息，不复述代码）：
   - 业务相关的特殊处理（补丁、绕过、隐含业务约束），读者没有背景看不懂，注释解释业务原因。
   - 复杂算法写明思路，整体策略加关键步骤的用意，源自论文/协议的注明出处。
   - 对外 API 保证读者知道怎么用：功能、参数/返回/副作用，不写实现细节。
4. **优先使用结构化标记**：给代码打状态标签，不替代解释注释。格式 `<前缀>: <描述>`，前缀全大写 + 冒号，描述具体（做什么/问题 + 方向）；`@<责任人> <日期>`、issue 号可选，要追溯时再附，如 `// FIXME @zhangsan 2026-08-14: 内存泄漏，改用 with 释放(#88)`；格式统一才能 grep 巡检全仓技术债，空泛的（`// TODO: 优化`）不如不写。标记是技术债的元信息，有长期工程价值，需要定期清理，有进有出，不能滥用。

### 2.2 禁止执行(NEVER DO)
1. 不写零信息量注释（"处理数据""优化性能"）。
2. 不复述代码（注释写代码说不出来的信息）。
3. 不滥用标记——空泛的 TODO 不如不写。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：代码上下文、语言规范（所在语言主流规范/项目既有风格）。
- 缺失时：项目风格不明 → 先看同类文件既有注释风格，无先例按语言官方规范。

## 3. 知识底座（CONTEXT）

### 3.1 结构化标记前缀

| 前缀 | 含义 |
|------|------|
| TODO | 待办 |
| FIXME | 已知缺陷 |
| NOTE | 非显然约束 |
| HACK | 临时方案 |
| ATTENTION | 可疑有雷 |
| OPTIMIZE | 性能待优化 |
| REVIEW | 请人复查 |
| DEPRECATED | 已废弃有替代 |

- 注释符随语言，**前缀词固定**：`<前缀>: <描述>`。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 判断该不该注
- 动作：先问能否靠改名/重构说清楚——能则不动；不能且是 2.1 ③ 三类（业务特殊处理/复杂算法/对外 API）才注释。
- 完成标志：注释必要性判定明确。

### Step 2: 确定写法
- 动作：按 2.1 ② 对齐语言规范与项目风格；写在要解释的代码旁，直说为什么。
- 完成标志：写法符合规范，无复述/无空话。

### Step 3: 打标记（按需）
- 动作：状态标签用 3.1 前缀，格式 `<前缀>: <描述>`，可附 `@责任人 日期` 与 issue 号。
- 完成标志：标记格式统一，可 grep 巡检。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```text
<注释符><前缀>: <具体描述>[@<责任人> <日期>][(#issue)]
// FIXME @zhangsan 2026-08-14: 内存泄漏，改用 with 释放(#88)
```

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| 前缀 | 用 3.1 固定前缀，全大写 |
| 描述 | 具体（做什么/问题 + 方向），不空泛 |
| 责任人/日期/issue | 可选，要追溯时再附 |

### 5.3 交付前自检
- [ ] 能改名/重构说清楚的地方没加注释
- [ ] 注释是代码说不出来的信息，无复述
- [ ] 标记前缀固定、格式统一
- [ ] 对齐了语言规范与项目风格

## 6. 示例

### 6.1 好的示例
**输入**：这段连接释放逻辑要不要加注释？
**输出**：加 `// FIXME @zhangsan 2026-08-14: 内存泄漏，close 只 catch 部分异常，改用 finally 归还(#88)`——业务原因代码看不出来，标记格式统一可巡检。

### 6.2 差的示例
**输入**：这段连接释放逻辑要不要加注释？
**输出**：加 `// 处理数据` 或 `// 释放连接`。
（零信息量/复述代码——违反 2.2①②，写了不如不写）
