# traft-code-docs 技能

项目离码文档管理：管理需求相关文档（prd / adr / test / review / progress）、工作流文档、参考文档的落盘与更新。

**职责边界**：
- 负责：离码文档的创建、更新、落盘、模板管理；按需求阶段推进。
- 不负责：写代码（`traft-code-implement`）、需求深挖（`traft-requirements`）、临时任务/周报（`traft-todos`）、vault 主页等非项目文档（`traft-obsidian`）。超出边界直接转交，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 是否触发 |
| --- | --- | --- |
| 落盘方案 | "整理头脑风暴结果，落盘方案" | 触发 |
| 建需求 | "创建一个新需求" | 触发 |
| 更新进度 | "更新项目进度" | 触发 |
| 沉淀知识 | "沉淀成一篇wiki" | 触发 |
| 需求深挖/写码 | "头脑风暴一下"、"帮我实现" | 不触发，转交 `traft-requirements`/`traft-code-implement` |
| 闲聊/泛泛提问 | "随便聊聊"、"你怎么看" | 不触发，交给默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. 通过用户审批才允许落盘操作。
2. 落盘完成后，告知用户变更文件的全局路径。
3. 如果需要方案配图或配图可以降低理解难度，向用户申请激活绘图技能。

### 2.2 禁止执行(NEVER DO)
1. 不未经审批落盘。
2. 不跳过模板直接手写（复制 `templates/` 对应模板）。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：需求名、项目归属；落盘内容。
- 缺失时：需求文件夹不存在 → 先建 `project/<repo>/<YYYYMMDD-需求名>/` 再落文档，如实告知新建路径。

## 3. 知识底座（CONTEXT）

### 3.1 目录结构
```text
<obsidian根目录>/
└── project/<repo>/             # 一项目一目录(≈ git repo)
    ├── reference.md            # 外部资料链接
    ├── wiki/                   # 项目知识性内容(环境/API/roadmap,跨需求复用)
    ├── workflow/               # 项目特定流程(发版/测试,可照着执行)
    ├── <YYYYMMDD-需求名>/      # 一需求一文件夹(日期前缀)
    │   ├── prd.md              # 需求与方案设计(阶段②)
    │   ├── adr.md              # 关键设计决策(一决策一张)
    │   ├── test.md             # 测试计划与结论(阶段③)
    │   ├── review.md           # 评估审查报告(阶段④)
    │   └── progress.md         # 进度(状态真源)
    └── assets/                 # 附件(方案图/截图)
```
- 每目录一个项目（≈ 一个 git repo），一项目内所有事情都放这层；项目可嵌套子项目；每需求一文件夹，命名 `YYYYMMDD-需求名`；子文档按需逐步添加，不要求全有。

### 3.2 模板（本技能 `templates/`，建需求时复制；也可 `skill://traft-code-docs/templates/<名>.md`）

| 文档 | 模板 | 用途 |
|------|------|------|
| 需求规格 | `templates/prd.md` | 需求背景、方案设计、验收标准 |
| 设计决策 | `templates/adr.md` | 背景、决策、备选、后果 |
| 测试 | `templates/test.md` | 测试计划与结论 |
| 评估审查 | `templates/review.md` | 双轴审查、需求达成确认 |
| 进度 | `templates/progress.md` | 状态真源,每阶段更新 |
| 周记 | 见 `traft-todos/templates/weekly.md` | 周级汇总(不计入单需求,由 traft-todos 技能管理) |

### 3.3 需求阶段（六阶段定义见 `traft-guideline` 3.1，此处只列文档产出）

| 阶段 | 输出文档 |
|------|----------|
| ① 头脑风暴 | `prd.md` 的「需求」部分（含「范围外」） |
| ② 方案设计 | `prd.md` 的「方案」部分 |
| ③ 实现 | 代码 + `adr.md` |
| ④ 验证 | `test.md` + `review.md` |
| ⑤ 发布 | 无 |
| ⑥ 沉淀 | wiki / 卡片 / 可复用技能 |

要点：④ 先 `impact` 看影响面再全量测试与全量评估，修完冒烟；每阶段结束把 progress.md 的 status 推进到下一阶段。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 建需求
- 动作：确认项目归属与需求名，复制对应模板到 `project/<repo>/<YYYYMMDD-需求名>/`（prd/adr/test/review/progress 按需）。
- IF 用户未审批 → 先展示要创建的文件清单，获批再落盘。
- 完成标志：需求文件夹存在，模板落位。

### Step 2: 更新文档
- 动作：按阶段更新对应文档（prd 需求/方案、adr、test、review、progress），改 progress.md 的 status。
- 完成标志：文档更新完成、status 推进；告知用户变更文件全局路径。

### Step 3: 申请配图（按需）
- IF 需要配图 → 向用户申请激活绘图技能（`traft-code-graph`）。
- 完成标志：获批后配图已嵌入/落盘 assets/。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```text
已落盘:
- <文件全局路径>（用途一句话）
进度: progress.md status → <阶段>
```

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| 已落盘 | 列变更文件的全局路径，不省略 |
| 进度 | 对应 progress.md 实际 status |

### 5.3 交付前自检
- [ ] 落盘前已获用户审批
- [ ] 文档按模板落盘，路径符合 3.1 结构
- [ ] 告知了变更文件全局路径

## 6. 示例

### 6.1 好的示例
**输入**：创建新需求"订单导出"，落盘方案
**输出**：
```text
已落盘:
- /vault/project/order/20260909-订单导出/prd.md（需求背景+方案+验收标准）
- /vault/project/order/20260909-订单导出/progress.md（状态真源）
进度: progress.md status → ② 方案
```

### 6.2 差的示例
**输入**：创建新需求"订单导出"，落盘方案
**输出**：未经审批直接写文件，且只给相对路径/不给路径。
（违反 2.1①②——必须审批、必须给全局路径）
