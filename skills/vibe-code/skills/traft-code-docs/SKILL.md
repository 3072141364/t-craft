# RULES

## 目录结构
- `project/` 每目录一个项目(≈ 一个 git repo)；一项目内所有事情都放这层。
- 项目可嵌套子项目；每需求一文件夹,命名 `YYYYMMDD-需求名`(如 `20290212-登录优化`)。
- 子文档按需逐步添加,不要求全有。
```text
<obsidian根目录>/
└── project/<repo>/             # 一项目一目录(≈ git repo)
    ├── reference.md            # 外部资料链接
    ├── wiki/                   # 项目知识性内容(环境/API/roadmap,跨需求复用)
    ├── workflow/               # 项目特定流程(发版/测试,可照着执行)
    ├── <YYYYMMDD-需求名>/      # 一需求一文件夹(日期前缀)
    │   ├── prd.md              # 需求与方案设计(阶段②)
    │   ├── adr.md              # 关键设计决策(一决策一张)
    │   ├── test.md             # 测试计划与结论(阶段③)
    │   ├── review.md           # 评估审查报告(阶段④)
    │   └── progress.md         # 进度(状态真源)
    └── assets/                 # 附件(方案图/截图)
```
- 需求归属于项目,每个需求单独一个文件夹(`YYYYMMDD-需求名`)。

## 需求目录结构

需求在 `project/<repo>/<YYYYMMDD-需求名>/` 下单独一个文件夹,子文档按需逐步添加:

模板统一放本技能 `templates/` 目录,建需求时直接复制对应模板:

| 文档 | 模板(相对技能目录) | 用途 |
|------|--------------------|------|
| 需求规格 | `templates/prd.md` | 需求背景、方案设计、验收标准 |
| 设计决策 | `templates/adr.md` | 背景、决策、备选、后果 |
| 测试 | `templates/test.md` | 测试计划与结论 |
| 评估审查 | `templates/review.md` | 双轴审查、需求达成确认 |
| 进度 | `templates/progress.md` | 状态真源,每阶段更新 |
| 周记 | 见 `traft-weekly/templates/weekly.md` | 周级汇总(不计入单需求,由 traft-weekly 技能管理) |

> 模板也可经 `skill://traft-code-docs/templates/<名>.md` 读取。

## 需求阶段

面对一个需求,按以下阶段推进;每阶段做什么、激活什么、产出哪份文档见下表。

| 阶段 | 做什么 | 输出文档 |
|------|--------|----------|
| ① 头脑风暴 | 搞清楚需求是什么、要做什么、**不做什么** | `prd.md` 的「需求」部分 |
| ② 方案设计 | 整理并落盘方案 | `prd.md` 的「方案」部分 |
| ③ 实现 | 写代码 | 代码 + `adr.md` |
| ④ 验证 | 先评审:影响面 → 全量 → 修复 → 冒烟 | `test.md` + `review.md` |
| ⑤ 发布 | 提交 → 合并主分支 →peer review → 上线 | 无 |
| ⑥ 沉淀 | 提炼可复用内容进 skill 仓库 | wiki / 卡片 / 可复用技能 |

要点:
- **① 头脑风暴**:产出 prd 的需求部分(含「范围外」= 明确不做什么)。
- **④ 验证先评审**:先 `impact` 看影响面,再全量测试与全量评估,修完冒烟;对应 test.md 与 review.md 两份产出。
- 每阶段结束把 `progress.md` 的 `status` 推进到下一阶段。
