# traft-requirements

接到含糊需求（feat / bugfix、新功能、改行为），目标是：动工前把「真正要解决什么」问清，产出**需求要点**；不写代码、不写方案文件。需求已明确、范围清楚的小改不走本技能，直接进实现。

## RULES

### ALWAYS DO
- **事实自查，决策问人**：现状、既有实现、配置、旧方案这类环境事实，自己读代码 / 文档 / obsidian vault 或派子代理查，不问用户；选型、取舍、优先级这类决策才问用户。
- **一轮问一批**：问题逐条编号，每条附推荐答案 + 一句话理由，用户可一键采纳或修正；答案依赖本轮未落定问题的，放后续轮次，不抢跑。
- **YAGNI**：剔除「万一以后要」的功能假设；模糊词（更好 / 灵活 / 易用）要么量化要么删。
- **化繁为简**：需求过大 / 含多个独立子系统时先拆分，别在细节里打转--按可独立交付、可独立验收的价值切片，不按技术层拆；定子项优先级与依赖，只深挖第一项，其余列为后续需求。
- **查旧方案**：深挖中 / 收尾时用 traft-obsidian 查 vault 的旧方案、踩坑、决策卡；查到的旧决策与本需求冲突，作为问题抛给用户定夺。

### NEVER DO
- 不写代码、不写方案文件、不进实现--**用户确认需求要点前是硬门槛**，需求多简单都适用。
- 不把能自己查到的拿去问用户；不猜没听过的答案。
- 不替用户拍板选型、取舍。

## 深挖流程

1. **探索上下文先**：读相关代码 / 文档 / 近期 commit、项目上下文（CLAUDE.md / AGENT.md / AGENTS.md 等）的技术约束，先摸清现状再提问；用 traft-obsidian 查本项目既有需求，命中就从其进度接着问，不重复深挖。
2. **画设计树**：需求拆成决策树，决策为节点、依赖为边；第一层骨架：真实意图 -> 约束 -> 边界 -> 风险 -> 验收标准 -> 旧方案。树在心里、轮次里问得出来即可，不用画给用户。
3. **前沿轮次追问**：每轮把「前提已落定」的问题一批全问（逐条编号 + 推荐答案），答案解锁下一轮；前沿问空、没有默默假设的分支，才算问完。
4. **按需上追问工具**（不强制每次用）：
   - **5-Whys**（症状与根因错位，bugfix 类）：定义问题（可观测事实）-> 迭代问 why（每层要证据）-> 识别根因（可操作 / 可预防 / 不可再分）-> 反向验证链（根因修了则逐层不发生）-> 定对策（止血 + 预防 + 检测）。反模式：停太早、归咎人、漏多因。
   - **first-principles**（质疑「是不是真该这么做」）：剥到问题本质（job-to-be-done）-> 挑全部假设（显式 + 隐式，逐条问是真约束还是惯常做法）-> 立不可约真值（业务不变量 / 物理约束）-> 从真值向上推（最小方案，每个加层要挣得复杂度）-> 验证推理链（每个决策可追到一条真值）。反模式：小事也用、否定一切既有方案、为理论纯度忽视现实约束。
5. **产出需求要点**：在对话内按模板呈现，用户确认后交接；要点要短，验收标准逐条可检查。
6. **交接阶段②**：提示用户激活 traft-code-docs 落盘--建 `projects/<项目>/requirements/<需求名>/`，把要点写进 prd.md 的「需求」部分，progress.md 状态推进到 ② 方案。

## 需求要点模板

```markdown
## 需求要点

**目标**：一句话说清要解决什么
**约束**：时间 / 技术 / 兼容性
**验收标准**：逐条可检查
**相关旧方案**：[[旧方案]]（vault 链接，无则留空）
**范围外**：明确不做的（防蔓延）
```
