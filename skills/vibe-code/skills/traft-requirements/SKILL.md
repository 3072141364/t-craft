# traft-requirements 技能

需求深挖 / 头脑风暴：动工前把「真正要解决什么」问清，产出**需求要点**。目标边界还不清时激活；需求已明确、范围清楚的小改不走本技能，直接进实现。

**职责边界**：
- 负责：需求深挖——现状自查、设计树追问、产出需求要点。
- 不负责：写代码（`traft-code-implement`）、写方案文件/落盘（`traft-code-docs`）、查 vault 旧方案之外的文档管理（`traft-obsidian`）。超出边界直接转交，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 是否触发 |
| --- | --- | --- |
| 需求头脑风暴 | "头脑风暴一下"、"聊聊需求"、"推荐方案，有什么优化方向" | 触发 |
| 新功能/修 bug | 接到 feat / bugfix、新功能、改行为，边界不清 | 触发 |
| 出需求文档 | "出一份 prd 文档" | 触发（深挖后交 code-docs 落盘） |
| 需求已明确 | 范围清楚的小改、直接说"按这个做" | 不触发，直接进实现 |
| 闲聊/泛泛提问 | "随便聊聊"、"你怎么看" | 不触发，交给默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. **事实自查，决策问人**：现状、既有实现、配置、旧方案这类环境事实，自己读代码/文档/obsidian vault 或派子代理查，不问用户；选型、取舍、优先级这类决策才问用户。
2. **一轮问一批**：问题逐条编号，每条附推荐答案 + 一句话理由，用户可一键采纳或修正；答案依赖本轮未落定问题的，放后续轮次，不抢跑。
3. **YAGNI**：剔除「万一以后要」的功能假设；模糊词（更好/灵活/易用）要么量化要么删。
4. **化繁为简**：需求过大/含多个独立子系统时先拆分——按可独立交付、可独立验收的价值切片，不按技术层拆；定子项优先级与依赖，只深挖第一项，其余列为后续需求。
5. **查旧方案**：深挖中/收尾时用 traft-obsidian 查 vault 的旧方案、踩坑、决策卡；查到的旧决策与本需求冲突，作为问题抛给用户定夺。

### 2.2 禁止执行(NEVER DO)
1. 不写代码、不写方案文件、不进实现——**用户确认需求要点前是硬门槛**，需求多简单都适用。
2. 不把能自己查到的拿去问用户；不猜没听过的答案。
3. 不替用户拍板选型、取舍。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：需求背景、可读的现状材料（代码/文档/vault）。
- 缺失时：现状材料不足 → 先读代码/文档/vault 补齐再提问，不空问。

## 3. 知识底座（CONTEXT）

- **设计树骨架**：真实意图 -> 约束 -> 边界 -> 风险 -> 验收标准 -> 旧方案（第一层）。
- **追问工具（按需，不强制每次用）**：
  - **5-Whys**（症状与根因错位，bugfix 类）：定义问题（可观测事实）-> 迭代问 why（每层要证据）-> 识别根因（可操作/可预防/不可再分）-> 反向验证链（根因修了则逐层不发生）-> 定对策（止血 + 预防 + 检测）。反模式：停太早、归咎人、漏多因。
  - **first-principles**（质疑「是不是真该这么做」）：剥到问题本质（job-to-be-done）-> 挑全部假设（显式+隐式，逐条问是真约束还是惯常做法）-> 立不可约真值（业务不变量/物理约束）-> 从真值向上推（最小方案，每个加层要挣得复杂度）-> 验证推理链（每个决策可追到一条真值）。反模式：小事也用、否定一切既有方案、为理论纯度忽视现实约束。
- **旧方案查询**：`traft-obsidian`（vault 旧方案、踩坑、决策卡）。
- **交接**：`traft-code-docs` 建 `projects/<项目>/requirements/<需求名>/` 落盘。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 探索上下文
- 动作：读相关代码/文档/近期 commit、项目上下文（CLAUDE.md / AGENT.md / AGENTS.md 等）的技术约束，先摸清现状再提问；用 traft-obsidian 查本项目既有需求，命中就从其进度接着问，不重复深挖。
- 完成标志：现状与既有需求已摸清。

### Step 2: 画设计树
- 动作：需求拆成决策树——决策为节点、依赖为边；第一层骨架见 3. 知识底座。树在心里、轮次里问得出来即可，不用画给用户。
- 完成标志：设计树骨架成形。

### Step 3: 前沿轮次追问
- 动作：每轮把「前提已落定」的问题一批全问（逐条编号 + 推荐答案），答案解锁下一轮。
- 完成标志：前沿问空、没有默默假设的分支，才算问完。

### Step 4: 按需上追问工具
- IF 症状与根因错位（bugfix 类）→ 5-Whys。
- IF 质疑「是不是真该这么做」→ first-principles。
- 完成标志：问题空间收敛。

### Step 5: 产出需求要点
- 动作：在对话内按 5.1 模板呈现，用户确认后交接；要点要短，验收标准逐条可检查。
- 完成标志：用户确认需求要点。

### Step 6: 交接阶段②
- 动作：提示用户激活 traft-code-docs 落盘——建 `projects/<项目>/requirements/<需求名>/`，把要点写进 prd.md 的「需求」部分，progress.md 状态推进到 ② 方案。
- 完成标志：交接明确，未自行落盘。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```markdown
## 需求要点

**目标**：一句话说清要解决什么
**约束**：时间 / 技术 / 兼容性
**验收标准**：逐条可检查
**相关旧方案**：[[旧方案]]（vault 链接，无则留空）
**范围外**：明确不做的（防蔓延）
```

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| 目标 | 一句话说清要解决什么 |
| 约束 | 时间/技术/兼容性，来自用户确认 |
| 验收标准 | 逐条可检查，不写模糊表述 |
| 相关旧方案 | vault 链接；无则留空，不编造 |
| 范围外 | 明确不做的，防蔓延 |

### 5.3 交付前自检
- [ ] 目标边界问清，无默默假设的分支
- [ ] 验收标准逐条可检查
- [ ] 未写代码、未落盘（交接给 code-docs）
- [ ] 现状事实已自查，未问用户能查到的事

## 6. 示例

### 6.1 好的示例
**输入**：想给系统加个导出功能
**输出**：
```markdown
## 需求要点

**目标**：订单列表支持按筛选条件导出 CSV
**约束**：数据量上限 10 万行；导出异步任务
**验收标准**：筛选后导出文件与列表一致；超限提示分批；导出记录可查
**相关旧方案**：[[导出功能旧方案]]
**范围外**：不做定时导出、不做导出模板定制
```
（问题逐轮问清后产出，验收可检查，范围外明确）

### 6.2 差的示例
**输入**：想给系统加个导出功能
**输出**：直接写代码或直接落方案文件。
（越过用户确认需求要点的硬门槛——违反 2.2 ①）
