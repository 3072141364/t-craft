# traft-code-review 技能

对一段改动做**双轴审查**：Standards 轴（代码本身对不对：5 维审查——质量/潜在问题/架构/测试/安全）+ Spec 轴（改动达没达成需求：对照 prd 验收标准）。两档：**轻量 / 深度（默认）**，定义见 3.1。只出报告不改码。

**职责边界**：
- 负责：双轴审查、需求达成确认、回归影响、出问题清单与可发布/需修结论。
- 不负责：改代码/代修复（`traft-code-implement`）、修 bug（`traft-code-debug`）、格式/lint（交工具）、代码查证（走 `traft-code-intelligence` 路由）。超出边界直接转交，不硬接。

## 1. 触发条件（TRIGGER）

| 场景 | 触发信号(关键词/典型句式) | 档位 | 是否触发 |
| --- | --- | --- | --- |
| 影响评估 | "评估一下影响"、"审下代码" | 轻量 | 触发 |
| PR 评审 | "PR 能合吗"、"这个 PR 有没有问题" | 深度 | 触发 |
| 审查改动 | "review 一下这个改动"、"帮我审下这段代码" | 深度（默认） | 触发 |
| 自查/发版把关 | "改完了检查一下"、"发版前审一遍" | 深度（默认） | 触发 |
| 需求实现/修 bug | "帮我实现"、"排查下这个 bug" | — | 不触发，转交 `traft-code-implement`/`traft-code-debug` |
| 闲聊/泛泛提问 | "随便聊聊"、"你怎么看" | — | 不触发，交给默认回复 |

## 2. 规则（RULES）

### 2.1 务必执行(ALWAYS DO)
1. **双轴都要看**：只审 Standards 漏掉需求达成，只核 Spec 漏掉代码质量；每条问题标注所属轴。
2. **拿改动用纯 git**：未提交 `git diff`、指定范围 `git diff <base..head>`、历史 `git log -p`；VCS 无关。
3. **查证走 `traft-code-intelligence`**：谁调用/影响面/执行流按其路由表（gitnexus / LSP / read 工具组），不肉眼硬追。
4. **问题带定位**：每条给出文件 + 行号（或 hunk），判断题标"可能 X"。
5. **结论当先**：报告按 5.1 结构交付，MR 元信息后第一个给出「结论:」行（可发布/需修 + 理由）。
6. **需求达成确认**：Spec 轴对照 prd.md 验收标准逐条核对成表（见 Step 3）；回归影响对照 prd「AI 须知的变更清单」预判 vs 实际。

### 2.2 禁止执行(NEVER DO)
1. 不改代码、不代修复——只出报告与建议。
2. 不审格式 / linter 能查的（空格/缩进/行长/命名）——交 lint / `make format`，报告里不列。
3. 不凭印象断言调用关系——用工具查证，有证据才写。
4. 不把启发式问题当硬违规——项目规范明确认可的压下不报（见 3.2 尾注）。

### 2.3 条件执行(CONDITIONAL)
- 需要的输入：改动（git diff/范围）、对应需求 prd.md（全量评估必需）。
- 缺失时：
  - 无 prd → 向用户确认需求要点后再核 Spec 轴，不臆造验收标准。
  - 报告要落盘 → 按 `traft-code-docs` 的 `templates/review.md` 走审批写入 `requirements/<需求名>/review.md`。

## 3. 知识底座（CONTEXT）

### 3.1 双轴与深度

| 维度 | 内容 |
|------|------|
| Standards 轴 | 代码本身质量：5 维审查（见 3.2）+ 行为准则 + 项目规范 |
| Spec 轴 | 需求达成：对照 prd.md 验收标准逐条核对 |
| 轻量（影响面评估） | Standards 扫 diff + 波及范围，无 spec 表 |
| 深度（默认，全量评估） | 双轴完整 + 需求达成确认 + 回归影响；研发阶段④必走 |

### 3.2 Standards 轴审查维度（5 维，逐维扫 diff 标"可能 X"）

| 维度 | 检查要点 |
|------|---------|
| 1. 代码质量 | 可读性；命名规范（神秘命名/取不出诚实名字）；代码重复（重复代码/霰弹式/发散式修改）；复杂度（消息链/中间人/被拒继承/投机性泛化/数据泥团/基本类型偏执/重复 switch/依恋情结） |
| 2. 潜在问题 | 空指针；资源泄漏（连接/句柄未归还）；并发问题（竞态/死锁/线程安全）；边界条件（空集合/极值/超时）；异常处理（吞异常/只 catch 部分异常） |
| 3. 架构设计 | 是否符合项目规范；模块依赖是否合理（循环依赖/依赖方向）；是否有更好的实现方式 |
| 4. 测试覆盖 | 是否缺少测试；测试场景是否充分（正常/边界/异常路径） |
| 5. 安全性 | 注入（SQL/命令）；越权（权限校验缺失）；敏感信息泄露（日志/响应/前端暴露） |

- 每条是判断题不是硬违规；项目规范明确认可的做法压下不报。
- linter / 类型检查能查的跳过（格式、命名交工具）。

### 3.3 相关技能路由
- 代码查证（调用链/影响面）→ `traft-code-intelligence`（gitnexus-impact-analysis，要结论别用快瞥）。
- prd/review 模板与落盘 → `traft-code-docs`（`requirements/<需求名>/`）。
- 可发布后的提交 → 用户发起时走 `traft-code-git`（审查自身不主动提交）。
- **约定变更时同步更新本节。**

## 4. 工作流程（WORKFLOW）

### Step 1: 定档定范围
- 动作：按 1. 触发条件或用户意图定档（轻量/深度，默认深度，见 3.1）；范围用 git 确定。
- 完成标志：档位与 diff 范围明确。

### Step 2: Standards 轴
- 动作：对照 3.2 五维基线逐维扫 diff，标"可能 X"引对应 hunk；再查外科手术式修改——每行改动能否直接追溯到需求，有没有顺手改无关代码/删无关死代码。
- 完成标志：diff 逐行扫过，问题带定位（文件 + 行号/hunk）。

### Step 3: Spec 轴
- 动作：读对应需求 prd.md（`traft-code-docs` 的 `requirements/<需求名>/`），验收标准逐条核对，产出达成确认表。
- IF 没有 prd → 向用户确认需求要点后再核。
- 完成标志：验收标准逐条成表（达成/未达成/存疑）。

### Step 4: 回归影响
- 动作：影响面走 `traft-code-intelligence`（`gitnexus-impact-analysis`）；对照 prd「AI 须知的变更清单」预判 vs 实际。
- 完成标志：影响结论有工具证据支撑。

### Step 5: 出报告
- 动作：对话内呈现，按 5.1 结构交付；要落盘时按 `traft-code-docs` 的 `templates/review.md` 走审批写入 `requirements/<需求名>/review.md`。
- 完成标志：报告按 5.1 结构交付；落盘已过审批。

### Step 6: 交接
- IF 可发布 → 交付结论；提交由用户触发（用户发起提交时才转 `traft-code-git`，审查自身不主动走 git）。
- IF 需修 → 列未完成项交回修改，修完重审。
- 完成标志：结论与下一步明确。

## 5. 输出规范（OUTPUT SPEC）

### 5.1 固定格式
```text
## 代码评审
- 标题: <MR标题>
- 作者: <作者>
- 分支: <源分支> → <目标分支，默认 master>
- 改动文件数: <N> 个
- 评估档位: 深度（默认）/ 轻量

结论: <可发布/需修 + 一句话理由>

## Standards 轴
### 1. 代码质量
<评价>
### 2. 潜在问题
<评价>
### 3. 架构设计
<评价>
### 4. 测试覆盖
<评价>
### 5. 安全性
<评价>

## spec 轴
### 1. 需求达成确认
| 验收标准 | 达成 | 证据 |
|---------|------|------|

```

（档位定义见 3.1；轻量不写 spec 轴。）

### 5.2 字段要求

| 字段 | 写作要求 |
|----|------|
| 标题/作者/分支/改动文件数 | MR 元信息，分支默认目标 master；缺失如实标注"未知"，不臆造 |
| 评估档位 | 轻量/深度（默认）；按 Step 1 定档 |
| 结论 | 开头一行可发布/需修 + 一句话理由 |
| Standards 5 维 | 每维给评价；问题带定位（文件:行号/hunk） |
| 需求达成确认 | 对照 prd 验收标准逐条，证据来自读到的代码/测试；无 prd 时经用户确认要点后核 |

### 5.3 交付前自检
- [ ] 双轴覆盖（全量）或声明了单轴（轻量），未漏 Spec
- [ ] Standards 5 维逐维给出评价，问题带定位，调用关系有工具证据
- [ ] 未列格式类问题（lint/format 交工具）
- [ ] 未改任何代码、未代提交，结论行给出可发布/需修 + 理由（提交由用户触发）

## 6. 示例

### 6.1 好的示例
**输入**：review 一下这次改动（git diff）
**输出**：
```text
## 代码评审
- 标题: 订单接口支持失败重试
- 作者: 小明
- 分支: feat/order-retry → master
- 改动文件数: 3 个
- 评估档位: 深度

结论: 需修——重试逻辑未实现（Spec 高优先级），其余维度无阻塞项。

## Standards 轴
### 1. 代码质量
命名清晰；src/order.ts:42 与 line 88 同形状逻辑，可能重复代码，可抽共享函数。
### 2. 潜在问题
src/order.ts:88 异常路径未归还连接，可能资源泄漏，建议 finally 归还。
### 3. 架构设计
符合项目分层；重试逻辑收在 retry 模块，依赖方向合理。
### 4. 测试覆盖
正常路径有单测；缺失败/重试耗尽两条异常路径用例。
### 5. 安全性
无注入/越权问题；日志未输出敏感字段。

## spec 轴
### 1. 需求达成确认
| 验收标准 | 达成 | 证据 |
|---------|------|------|
| 1. 下单成功入库 | 达成 | 单测通过 |
| 3. 失败可重试 | 未达成 | 无重试分支 |
```
（MR 元信息 + 档位 + 结论行开头 + 5 维评价 + 达成表）

### 6.2 差的示例
**输入**：review 一下这次改动
**输出**：只列"第 5 行多了个空格"、"缩进不对"；或凭印象说"这个函数没人调用"。
（格式问题交 lint；调用关系无工具证据——违反 2.2）
