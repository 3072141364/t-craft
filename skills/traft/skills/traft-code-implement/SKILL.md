# traft-code-implement 方案实现

研发阶段③：把已对齐的需求（prd）落成代码。**头脑风暴已经思考过了**--需求、边界、验收标准都在 prd.md，实现不再重新深挖；这里的"思考"是把方案落成具体改动规划，并暴露实现中才浮现的新问题。

## RULES

### ALWAYS DO
- **先读 prd 再写码**：动手前读 `traft-project-docs` 落盘的 prd.md（需求 + 方案 + 验收标准）；方案不清楚或与 prd 冲突，先问，不擅自改已定的事。
- **先思考再动手**：写码前默一遍要改哪些文件、用什么衔接点、怎么验证；有多种解读全呈现，有更简单方案 push back，说不清就停下问--不默默替用户选。
- **简洁优先**：解决问题的最小代码；不写要求之外的功能；单次使用不抽象；不为不可能发生的场景写错误处理；写多了（200 行本可 50 行）重写。自问"资深工程师会说过度复杂吗？"
- **外科手术式修改**：只动该动的；不顺手优化相邻代码 / 注释 / 格式；匹配既有风格；发现无关死代码**指出来**不删；移掉自己改动导致无用的 import / 变量 / 函数。每行改动可追溯到需求。
- **用查证与注释**：调用链 / 影响面走 `traft-code-intelligence`；注释遵循 `traft-code-comment`。
- **交付审核，不代提交**：实现与验证后，把改动与结果展示给用户审核；提交由用户确认后触发（走 `traft-git-flow`），本技能不提交。

### NEVER DO
- 不重新深挖已对齐的需求（那是阶段①）；不擅自改 prd 已定的边界 / 验收标准。
- 不做超出 prd 的投机功能、不加"万一以后要"的抽象。
- 不顺手改无关代码、不删既有死代码（除非被要求）。
- 不手动 git 提交、不自动 push。

## 流程

1. **读 prd**：`requirements/<需求名>/prd.md` 的需求 + 方案 + 验收标准。
2. **规划改动**：列改动文件 / 模块，说清衔接与验证方式；有疑问先问。
3. **写码**：按 RULES 落码（简洁、外科手术；查证 / 注释走对应 skill）。
4. **验证**：跑 prd 相关测试 / make 目标（走 `traft-make`，含 `make format` / `make lint`）；对照验收标准。
5. **交付审核**：展示改动与验证结果，等用户确认；提交由用户触发（走 `traft-git-flow`）；重要设计决策记 adr（`traft-project-docs`，落盘需审批）。
