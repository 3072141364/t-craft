# RULES
1. 非必要不注释，先改名、再重构，注释是最后手段。
  - 函数名、类名、成员名见名知义，能靠改名说清楚的，不加注释。
  - 长函数、晦涩逻辑先重构（拆函数、降耦合），重构解决不了的才注释，别拿注释给坏代码打补丁。

2. 注释写法：格式遵循所在语言的主流规范，不跨语言混用；内容简单明确，直指问题。
  - C++：遵循 Google C++ Style Guide。
  - Python：注释遵循 PEP 8规范。
  - 其他语言：先对齐项目同类文件的既有注释风格，无先例再按该语言官方 / 主流规范写。
  - 写在要解释的代码旁，直说为什么这么写，不铺垫背景、不绕弯子。
  - 一句话能说清的不写段落；零信息量的模糊概括（「处理数据」「优化性能」）写了不如不写。

3. 以下情况必须注释，注释写代码说不出来的信息，不复述代码：
  - 业务相关的特殊处理（补丁、绕过、隐含业务约束），读者没有背景看不懂，注释解释业务原因。
  - 复杂算法写明思路，整体策略加关键步骤的用意，源自论文 / 协议的注明出处。
  - 对外 API 保证读者知道怎么用：功能、参数 / 返回 / 副作用，不写实现细节。

4. 优先使用结构化标记：给代码打状态标签，不替代解释注释。
  - 使用标准前缀：TODO 待办、FIXME 已知缺陷、NOTE 非显然约束、HACK 临时方案、ATTENTION 可疑有雷、OPTIMIZE 性能待优化、REVIEW 请人复查、DEPRECATED 已废弃有替代；注释符随语言，前缀词固定。
  - 格式 `<前缀>: <描述>`，前缀全大写 + 冒号，描述具体（做什么 / 问题 + 方向）；`@<责任人> <日期>`、issue 号可选，要追溯时再附，如 `// FIXME @zhangsan 2026-08-14: 内存泄漏，改用 with 释放(#88)`；格式统一才能 grep 巡检全仓技术债，空泛的（`// TODO: 优化`）不如不写。
  - 标记是技术债的元信息,有长期工程价值，需要定期清理，有进有出，不能滥用。
