# ADR(关键设计决策)

> project-doc 的附属文档:设计决策记录(adr.md)怎么写。实现前记录关键设计决策 / 权衡时读本文。落点 `projects/<名>/requirements/<需求名>/adr.md`,模板在 skill 仓库 `assets/templates/adr.md`。

## 定位

记录一个需求的**关键设计决策**:做了什么选择、为什么、放弃了什么、后果如何。追加式——**一个决策一张,不修改历史**。

- **本需求级**(`requirements/<需求名>/adr.md`):该需求实现前的关键技术取舍。
- 影响整个项目、跨需求的架构决策,提升到项目级(项目 wiki 或 ADR 汇集)记录。

## 骨架

```markdown
---
title: <决策主题>
type: feat
project: <项目名>
status: ②方案
date: <日期>
tags: []
---

## 背景
为什么需要这个决策(约束、上下文)。

## 决策
选了什么(一句话 + 关键细节)。

## 备选方案
考虑过哪些、为什么没选。

## 后果
正面 / 负面、可回退性。
```

## 什么时候写

- **实现前**:关键取舍出现时先写——接口选型、数据模型、并发模型、第三方依赖等。
- **不写**显而易见的决策;写「有真实取舍、回头会想不起来为什么」的。

## 规则

- **一个决策一张 adr**,同一需求的多个决策追加在同一文件的不同章节,或拆多张(按复杂度)。
- **先决策后实现**:大方向进 adr 后再写代码,避免实现完才记导致记录失真。
- **与 prd 分工**:prd 记最终方案,adr 记为什么选它;两者互相链接。
- **与 review 分工**:实现后若决策被推翻,在 adr 追加「修订」,不改原决策段落。
