# PRD(需求/方案规格)

> project-doc 的附属文档:需求/方案文档(prd.md)怎么写。写方案 / 需求 / PRD / spec、把需求要点落成设计时读本文。落点 `projects/<名>/requirements/<需求名>/prd.md`,模板在 skill 仓库 `assets/templates/prd.md`。

## 定位

接过 brainstorm 的**需求要点**(目标/约束/验收标准/相关旧方案/范围外),或用户直接给的需求描述,**不重新采访**——只综合已对齐的内容(to-spec 思想:synthesis not interview)。产出规格化需求文档,落 vault。

## 骨架(按读者分章)

文档分两块读者:**用户读**(自己与同事)的主体内容,与**AI 读**(便于更好实现)的须知。候选方案/权衡是头脑风暴过程,不进文档——文档只记**最终方案 + 优缺点**。

```markdown
---
title: <需求名>
type: feat            # feat/bugfix/debug/hotfix/refactor/docs/chore(与 progress.md 一致)
project: <项目名>
status: ②方案
date: <日期>
summary: <一行全文概述,供查询 3-tier 分级读用>
tags: []
---

# 📋 <需求名>

<!-- 用户读:自己与同事 -->

## 需求背景
清晰的问题陈述:用户面临什么问题,为什么值得解决,从用户视角。
含:目标一句话 + 成功标准(可量化)。

## 方案设计
**最终选定的方案**(不搬候选过程)。
- **设计描述**:怎么做。模块/接口/架构/API 契约/schema 变更。
  不含具体文件路径或代码片段(易过时);例外:prototype 产出的状态机/reducer/schema/type shape 可内联,标注来自 prototype。
- **方案设计图**(按需,增加表现力):需要架构/流程/泳道/C4 图时,联动 fireworks-tech-graph 生成 PNG,存 `projects/<名>/assets/`,嵌入 `![[图名.png]]`。不需要图就不画。
- **方案优缺点**:pros/cons,直说。

## 项目收益
为什么值得做:价值/收益/达成什么。可量化。把"值得"讲清楚。

## 行动清单
怎么一步步做:阶段拆解/实现步骤序列。每步指向可验证目标(借 karpathy 的目标驱动:"步骤X -> 验证:[检查]")。
给用户看的怎么做,不是给 AI 的任务粒度。

## 验收标准
逐条可检查的完成判据:做了什么算做完。每条能验。
此节是阶段④ review.md 逐条确认需求达成的依据。

<!-- AI 读:便于更好实现 -->

## AI 须知
写给 AI 的实现约束,统筹以下内容:
- **范围外**:明确不做什么,防蔓延。
- **代码变更清单**:改动模块/文件类、新增 vs 修改、依赖关系(借 code-intelligence `detect_changes` / gitnexus `impact`)。
- **测试决策**:测哪些模块、用什么 seam、prior art。
- **其他实现约束**:项目 CLAUDE.md 硬约束摘要。
```

## 流程

1. **取输入**:读 brainstorm 产出的需求要点(对话内,若上游走过);否则从用户当前需求描述取。不重新采访。
2. **探索代码库**(若未探索):读相关代码/CLAUDE.md,用项目领域词表。尊重相关 ADR。
3. **勾测试 seam**:草拟测试切入点(优先既有、最高 seam),与用户确认,写进「AI 须知」测试决策。
4. **起草**:按上述骨架,按读者分章。用项目领域词,不写 boilerplate。
5. **落盘**:调 obsidian-kb 写 `prd.md`(从 skill 仓库复制模板 `assets/templates/prd.md`);`progress.md` 的 `status` 改为 `②方案`。代码仓库留指针(`> 方案见 Obsidian: [[<需求名>]]`)。
6. **自审**:扫占位(TBD/TODO/空节)/矛盾/歧义/范围(是否需拆子方案);修完再交付,不复审。
7. **用户审**:交付后请用户审,要改则改 + 重跑自审。

## HARD-GATE

**prd 用户确认前,不进实现、不写代码。** 这条适用于每个需求——"简单"需求也要落文档(可短,但必须落 + 确认),因为简单处正是未经检验假设造成浪费的地方。

## AI 须知节的设计意图

把写给 AI 的约束统筹进一节,而非散落:用户读主体时不被实现约束打断;AI 实现时聚焦读「AI 须知」拿到范围外、变更清单、测试决策、硬约束。读者意图分明,文档清爽。

## 与 adr 的分工

设计过程中的**关键决策与权衡**记 `adr.md`(追加式);prd 只记最终方案 + 优缺点,不搬决策过程。
