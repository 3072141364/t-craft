# 术语提炼(用术语降低沟通成本)

> 业务场景描述啰嗦、反复解释同一件事、跨角色沟通出现歧义时,提炼一个简短术语,把整段场景压缩成一个词。**术语是沟通的压缩算法:一次定义,处处复用。**

## 术语使用优先级(写文档时,三级)

写文档描述**特定场景 / 需求 / 流程**时,按这个优先级走——不跳过、不反过来:

1. **术语库优先**:场景在 [`terms.json`](terms.json) / 项目术语表里已有现成术语 → **直接用,不新造**。
2. **其次提炼**:库里没有,但场景复杂、反复出现、值得命名 → **提炼新术语**(简短名词 + 一句话定义 + 例子),记入项目术语表。
3. **自然语言兜底**:场景简单、一次性、不常复用 → **用自然语言描述**,不为提炼而提炼。

**术语是降低沟通成本的手段,不是 KPI**——该用自然语言时别硬造词;该用术语时别绕一大段。

## 什么时候才提炼(第二级才走到)

- 同一件事被反复解释,或不同人说法不一。
- 一段业务场景要绕很多话才讲得清(多个约束、多个参与方、多个原因)。
- 需求 / 方案 / 会议里多次出现「就是那个……」(指代不清)。
- 跨角色(研发、测试、客户、采购)沟通同一个概念,各自理解有出入。

没有这些信号 → 直接走第三级(自然语言),不提炼。

## 提炼流程

1. **查库**:先在 [`terms.json`](terms.json) + 项目术语表里找现成术语。
   - **命中** → 复用,结束。
2. **判断是否值得命名**:未命中时,对照上面「什么时候才提炼」——没有触发信号 → 自然语言描述,结束。
3. **提炼**(值得命名时):用一个简短名词(2-6 字为宜)概括场景,给一句话定义 + 典型例子。
4. **记录**:术语在 prd 里首次定义,写入项目术语表,后续文档 / 讨论统一用它。
5. **沉淀**:跨项目通用的术语可提炼进 skill 仓库的 `terms.json`,随插件生效。

## 提炼规则

- **简短可念**:2-6 字的名词,会议里说出来对方不尴尬。「双域通信」好,「跨域异构通信适配统一抽象层」差。
- **一个术语只描述一个场景**:场景变了就新提,别让一个词背上多个意思。
- **覆盖得住场景**:术语要能把「问题 / 场景 / 为什么这样做」压缩进去,听到的人能还原大意。
- **不与其他术语冲突**:先查 `terms.json` 与项目现有术语,不撞车。
- **贴合领域习惯**:能用领域标准词(HIL / SIL / 网关 / 容器)就用标准词,不另起炉灶。

## 为什么能降低沟通成本

- **压缩信息**:一长段约束用一个词承载,讲述成本从一段话降到两三个字。
- **建立共识**:定义一次、全员引用,消除「我以为的和你说的一样」的歧义。
- **可追溯**:术语在 prd 里定义、在 adr 里记决策,概念有出处,新人能查。

## 示例

| 场景描述 | 命中优先级 | 术语 / 自然语言 |
|---------|-----------|----------------|
| 仿真和实车通讯存在诸多不便利,各自有自己的协议和逻辑(复杂、反复出现) | ② 提炼 | **双域通信** |
| 台架上资源充足,跑一个测试任务浪费资源,可用虚拟隔离并行跑多个(复杂、值得命名) | ② 提炼 | **片内多环境模拟** |
| 一个只在某页面用一次的导入按钮的等待逻辑(简单、一次性) | ③ 自然语言 | 直接描述,不提炼 |
| 「客户说那个校验不通过」——库里已有 | ① 术语库 | 用项目术语表的现成术语 |

## 与 prd / adr 的关系

- **prd**:术语在需求规格里**首次定义**(术语表小节),正文用术语,不反复展开场景。
- **adr**:「为什么用这个术语而不用那个」是设计决策,记 adr。
- **progress / 周报**:用术语描述需求进展,一句话说清在做什么。
- **术语提炼是写作前的动作**,不单独成文档类型——它是 prd/adr/test/review 共用的前置能力。
