
# Brainstorm

> code-guidelines 的附属文档:研发流程**阶段①**的需求深挖 / 头脑风暴。接到 feat/bugfix 要做新功能或改行为前读本文,和用户一起深挖真实意图、约束、边界、风险、验收标准,查 vault 旧方案,产出需求要点。

研发流程阶段①:接到需求后、动手设计前,先深挖需求、头脑风暴。避免直接跳进实现,先把"真正要解决什么"弄清,产出**需求要点**交给阶段②(obsidian-kb 写方案)。

**设计意图**:LLM 容易拿到一句话需求就开写,跳过"这是真问题吗/有约束吗/怎么算做完"。brainstorm 在动笔前强制对齐,把含糊需求压成可检查的要点。产出物是**需求要点**(短),不是长方案——长方案是阶段② obsidian-kb 的职责,brainstorm 在对话内交付要点即可。

## 何时触发

**显式 + 意图匹配**。以下场景触发:

- 用户说"深挖需求""头脑风暴""先别写码,聊聊需求""这个需求不清楚""帮我理一下要做啥"等。
- 接到 feat/bugfix,需求描述含糊或范围不清,动手前需要对齐。
- 做新功能 / 改行为前,要先确认真实意图与边界。

**不触发**:

- 需求已明确、范围清楚的小改(直接进实现)。
- 只是查看代码、闲聊、查 git 状态。
- 纯执行性任务(跑测试、格式化、提交)。

## 前置:读取项目约定(不硬编码)

本 skill 跨项目复用。每次触发先发现项目约定:

1. **读项目 `CLAUDE.md`**:提取本项目的技术约束、模块布局、规范文档位置、分支与提交规则。若 CLAUDE.md 引用了规范文档(如 `docs/development.md`),一并读。
2. **查 vault 对应项目**:读 CLAUDE.md 的同时,优先用 obsidian-kb 模块二(query.md,3-tier 读)查 vault 的 `projects/` 有没有当前项目的文件夹;有则进一步查其 `requirements/` 是否已有匹配需求(同名 / 同主题的历史需求、进行中的需求)。命中了就是现成上下文——历史需求的 prd / 踩坑 / 决策直接进设计树,避免重复深挖已对齐过的东西;本次需求若是既有需求的延续,从它的进度接着问,而非从零开始。
3. **约定优于配置**:探测标准位置(根目录 `README.md`、`docs/`、`package.json` / `pyproject.toml` 等)了解项目栈与结构。
4. **可选描述文件**:`.claude/skills-config.json` 之类的显式覆盖。

以文件实际内容为准,不凭记忆。若项目 CLAUDE.md 未定义某些约定,用下文默认。下面各节的方法结合从 CLAUDE.md 读到的项目约束来执行。

**可调用的子 skill**:`obsidian-kb`(obsidian-skills plugin 内)查 vault 旧方案、沉淀方案。凡查 vault——前置的项目/需求定位、深挖中与收尾时的旧方案检索——都走 obsidian-kb 模块二(query.md)的 3-tier 读省 token。

## 核心:需求深挖引擎

引擎是**设计树 + 前沿轮次**的追问:把需求拆成决策树,每轮批量问「现在就能问的所有问题」,每问附推荐答案;事实自己查,决策交用户。

### 1. 探索上下文先

提问前先摸清现状,避免问已能从代码答的问题:

- 读相关代码、文档、近期 `git log`,了解项目现状与既有实现。
- 从项目 CLAUDE.md 读技术约束、模块边界。
- 用 code-intelligence(gitnexus `query` / codegraph `explore`)摸清相关调用链,若已索引。
- **事实是自己的活,不是用户的**:上面是提问前的摸底;深挖中冒出的新事实问题(某配置在哪、某接口谁在用)同样先查——自己读或派子代理,查不到才轮到用户。

### 2. 把需求画成设计树

把需求拆成一棵决策树:**每个决策是一个节点,它的答案分叉出依赖它的子决策**。深挖维度是树的第一层骨架:

```
真实意图 → 约束 → 边界 → 风险 → 验收标准 → 旧方案
```

依赖关系才是这棵树的形状:意图没定,该问哪些约束无从谈起;边界没定,风险清单也不成立。维度顺序只是起点参考,具体形状因需求而异(风险可能同时挂在多个节点下)。树不用画给用户看,心里有树、轮次里问得出来即可。

### 3. 前沿轮次:一轮问一批

- **前沿 = 前提已落定的那些决策**——不用猜没听过的答案、现在就能问的问题。每轮把前沿**一批全问**:逐条编号,每问附推荐答案,等用户答完再算下一轮。已落定的答案把前沿往外推,解锁依赖它的问题。
- 问题的格式:

```
❓ **Q1 - <问题标题>**: <问题正文,可多段;选项优先给 A/B/C>
   ➡️ 推荐:<推荐答案 + 一句话理由>
```

- **不抢跑**:答案依赖本轮仍未落定问题的,放到后面轮次,不猜答案。
- **事实自查,决策问人**:前沿问题需要环境事实(代码、文档、工具状态)时,派子代理去查,不把能自己查到的拿去问用户。**查着不堵**:跑着的探索算一条未落定前提,只有它下游的问题等它,前沿里其余的照问。
- **推荐答案要真推荐**:给理由,用户可一键采纳或修正,不是走过场;YAGNI,剔除「万一以后要」的功能假设。
- **前沿问空才算问完**:每条分支都走到、没有默默假设的东西,才进「产出与交接」。若一个答案分叉出太多新问题(树铺得太开),先回到范围检查拆解。

### 4. 范围检查

若需求描述了多个独立子系统(如"做一个带聊天、文件、计费、分析的平台"),**先提示拆解**,别在细节里打转:

> 这个需求含多个独立块(列出),一次对齐太大。先拆成子项,定优先级与依赖,然后只深挖第一项。

拆解后再对第一项走正常深挖流程。避免在一个会话里铺得过开。

### 5. 联动查旧方案

「vault 里有没有旧方案」是一条环境事实,不是用户决策——按事实自查原则,自己查,别拿去问用户。前置第 2 步已按项目定位查过一轮,这里补**跨项目 / 跨主题**的检索:

- 深挖中或收尾时,用 obsidian-kb 模块二检索 vault(3-tier 读:按 summary 判相关性,无关跳过 / 弱相关只读概述 / 强相关精读全文),省 token。
- 找可复用设计、避免重复踩坑。找到的相关卡片,收进需求要点的"相关旧方案"链接;查到的旧决策若与本需求冲突,作为前沿问题抛给用户定夺。
- 直接走 obsidian-kb 模块二(query.md)的 3-tier 读。

## 追问工具(可选,按需)

只在深挖到特定卡点时调用,**不强制每次走**。判断用哪个:

### 遇「症状 vs 根因」不清 → 5-Whys

需求表面问题与根因可能错位时(常见于 bugfix 类需求),按精简 5 阶段走:

1. **定义问题**:陈述为可观测事实(什么行为、何时、何组件、什么影响),别"系统慢"这种模糊话。
2. **迭代问 why**:每答一层,再问"为什么",每层要证据(日志/代码/配置),不只凭猜。
3. **识别根因**:可操作(能动手改)、可预防(改了能防复发)、不可再分(再问 why 无新动作)。
4. **反向验证链**:从根因正向推,"若根因修了 → 上层不发生 → ... → 问题不出现",链断则回看。
5. **定对策**:立竿见影(止血)+ 预防(防复发)+ 检测(预防失效时早发现)。

**反模式**:停太早(根因还是症状);归咎人(应是流程/系统,不是"开发者失误");单线程漏多因(多分支用树图)。

### 遇「假设存疑 / 方案是否最优」→ First Principles

质疑"是不是真该这么做"、挑战既有约定时,按精简 5 阶段走:

1. **剥到问题本质**:撇开实现细节,核心要解决的 job-to-be-done 是什么?成功标准?
2. **挑所有假设**:显式假设(明说的)+ 隐式假设("一直都这样""行业标准说")逐条列、逐条问"这是真约束,还是惯常做法?"。
3. **立不可约真值**:物理/数学约束、业务不变量、用户根本需求——能再分吗?可证伪吗?违反了必败吗?
4. **从真值向上推**:最小满足真值的方案是什么?每个加层都要为自己挣得复杂度。
5. **验证推理链**:每个设计决策能否追到一条真值?弱链在哪?什么会压垮它?

**反模式**:为每个小决策都用(留给有长期影响的重要决策);否定一切既有方案("揭示更好推理,而非保证最优解");为理论纯度忽视现实约束。

## 产出与交接

### HARD-GATE:需求要点确认前不进实现

深挖完,产出**需求要点**展示给用户。**用户确认前,不写代码、不写方案文件、不调实现 skill。** 这条适用于每个需求,不论看起来多简单——"简单"需求正是未经检验的假设造成最多浪费的地方。要点可以短(真正简单的需求几行就够),但必须呈现并获确认。

### 需求要点模板

确认后,在对话内呈现(不落盘文件——落盘是阶段② obsidian-kb 的事):

```markdown
## 需求要点

**目标**:一句话说清要解决什么
**约束**:时间 / 技术 / 兼容性
**验收标准**:可检查的条目(逐条能验)
**相关旧方案**:[[旧方案1]] [[踩坑2]](vault 链接,无则留空)
**范围外**:明确不做的(防止蔓延)
```

要点要短、要硬:**目标**一句话,**验收标准**逐条可检查,**范围外**显式列。模糊词("更好""灵活""易用")要么量化要么去掉。

### 交接阶段②

要点确认后,提示用户进阶段②——用 obsidian-kb 把方案写到 vault。可复用过渡提示:

> 需求要点已确认。**建需求文件夹 + progress.md(status ①头脑风暴)**:`projects/<名>/requirements/<需求名>/`(模板 `obsidian-kb/assets/templates/progress.md`),规则见 obsidian-kb 附属文档 progress.md。下一步进阶段②:project-doc(读附属文档 prd.md)把要点落成 prd.md,并把 progress.md 状态改为 ②方案。

到此 brainstorm 结束,不自行进方案设计或实现。

## 通用约定

- **每步确认**:产出需求要点前展示给用户确认,不擅自进实现。
- **以项目文件实际内容为准**:项目约定从 CLAUDE.md / 规范文档读,不凭记忆。
- **不擅自进实现**:深挖阶段只产出需求要点,不写代码、不写方案文件。
- **保持简洁**:不啰嗦重复,只在需要用户决策时才询问;能自己读代码答的不问用户。
- **失败要明确**:读不到的关键约定(如找不到 CLAUDE.md),停止并提示,不凭空假设。
