# 结构化注释标记(跨语言)

`TODO` / `FIXME` / `NOTE` / `HACK` / `XXX` / `OPTIMIZE` / `REVIEW` / `DEPRECATED` 八个标准前缀。写代码 / 审代码时的固定基线——和语言无关(Python `#`、C++/JS `//`、bash `#`、Lua `--` 注释符随语言,前缀词固定)。

**和"解释性注释"的区别**:这套标记不解释代码,而是给代码打**状态标签**——待办、已知缺陷、临时方案、待复查。它们是技术债的元信息,有长期工程价值,不属于"复述代码该删"那一类。但正因为是债,有进有出,不能泛滥。

两条约束:

- **标记是债,要还**:加了标记就要有清理计划(排进后续任务 / 带 issue 号);只加不清、堆积成百上千条不处理的,标记失去信号价值,等同没标。
- **别滥用**:别给正常实现打 `HACK`,别给还在正常用的核心 API 打 `DEPRECATED`。标记是"这里和理想状态有偏差"的信号,没偏差就别打。

## 逐标记

每条格式:`<前缀> @<责任人> <日期>: <具体描述>`(元信息可选但推荐,见下「管理约定」)。下面例子为简洁省略元信息,完整格式见末尾示例。

- **TODO** -- 计划要做、当前不影响运行的功能或优化。
  - 用:明确的后续事项,当前不阻塞,但写下来防忘。
  - 别用:当前正在做的事(直接做,别标);已排进 issue 的(标 issue 号即可,别重复埋);**空泛描述**(`// TODO: 优化` 是反例——优化什么?改成 `// TODO: 将数组遍历改为 Set 查找,提升重复校验性能`)。
  - 例:`// TODO: 将数组遍历改为 Set 查找,提升重复校验性能`

- **FIXME** -- 已知缺陷 / 隐患,该尽快修。
  - 用:你知道这里有错、近期会修,但此刻先放过。**说清具体问题 + 建议修复方向**,别只标 `// FIXME: 这里有问题`——后人不知道往哪修。
  - 别用:重大已知 bug 长期搁置——那该开 issue 正式跟踪,埋 FIXME 会让人误以为"近期修"。FIXME 是"我知道、近期清",不是"永久停尸"。
  - 例:`// FIXME: 此处内存泄漏,资源未用 with 释放,改用 contextmanager(#88)`

- **NOTE** -- 重要提示:设计决策、背景、非显然约束。
  - 用:代码读不出来的"为什么这么定"(如某参数必须 >0 的外部约束),给读者锚点。
  - 别用:复述代码或显而易见的事。
  - 例:`// NOTE: 此参数必须大于 0,下游除法依赖`

- **HACK** -- 非常规、不优雅的临时方案,后续重构。
  - 用:为绕过紧急问题(下游 bug、兼容性)写的将就代码,明确它不是最终形态。
  - 别用:合理的实现(别把正常代码叫 hack 显眼);用了就要排重构,别让 HACK 常驻变"合法"技术债。
  - 例:`// HACK: 临时绕过 SDK v3 的空指针 bug(#120),升级到 v4 后移除`

- **XXX** -- 潜在风险 / 可疑 / 极端情况可能失效。
  - 用:你不确定这里会不会出问题,比 FIXME 更"没把握"——FIXME 是"确定有错",XXX 是"怀疑有雷"。
  - 别用:已确定的问题(那用 FIXME);无依据的猜测(要么验证要么删,别留模糊焦虑)。
  - 例:`// XXX: 此算法在输入超 10^6 时可能 OOM,未压测验证`

- **OPTIMIZE** -- 性能待优化。
  - 用:确认有性能影响、但当前不是优先级,标记后续优化。
  - 别用:无依据的过早优化("这循环可能慢"——测了吗?);真要优化且现在能做就做,别标着拖延。
  - 例:`// OPTIMIZE: 循环内单条 DB 查询改批量预取`

- **REVIEW** -- 请求复查某段逻辑 / 设计。
  - 用:你拿不准、想让人重点看这段(并发锁、边界处理、算法正确性)。
  - 别用:已经复查过的(删标);替代正式 PR review 流程(那是另一回事)。
  - 例:`// REVIEW: 确认此并发锁的加锁顺序是否会导致死锁`

- **DEPRECATED** -- 已废弃,将移除,有替代。
  - 用:旧 API/函数不再推荐,提醒调用方迁移。
  - 别用:还在正常用的核心 API(标了反而制造恐慌);标了就要有替代方案并在文档写清迁移路径,否则别标。
  - 例:`// DEPRECATED: 用 new_method() 代替,2.0 移除`

## 管理约定

- **格式统一:全大写 + 冒号**:统一 `TODO:` / `FIXME:` 全大写带冒号,别 `todo:` / `Todo`——大小写不一就 grep 不全,视觉也不一致。尽量单行;描述较长另起一行写**普通注释**(无前缀),别让前缀标记行跨行。
- **内容要具体,别空泛**:`// TODO: 优化` 没价值(优化什么?);`// FIXME: 这里有问题` 没方向(往哪修?)。描述写清**做什么 / 具体问题 / 建议方向**,让后人不用重新读代码就知道怎么动手。
- **附元信息(可选但推荐)**:团队开发中,标记后附责任人 + 日期(+ 可选 issue 号 / 预计处理时间),方便追溯。格式:`<前缀> @<人> <日期>: <描述>`。
  - 完整示例:`// TODO @zhangsan 2026-08-14: 补充单元测试`
  - 带 issue:`// FIXME @zhangsan 2026-08-14: 内存泄漏,改用 with 释放(#88)`
  - 责任人知道债主是谁,日期让"近期清"有参照(标了一年的 FIXME 显然不是近期)。
- **可检索**:统一前缀 + 全大写 + 冒号,`grep -rn "TODO:\|FIXME:\|XXX:"` 能一把巡检全仓技术债。这也是格式必须统一的原因——大小写 / 有无冒号一不一致就漏。
- **定期清理,优先 FIXME**:标记不是代码的"永久居民"。Code Review 和版本迭代时定期清已完成 / 已过时的标记;**FIXME 优先于 TODO 处理**——FIXME 是已知缺陷(带雷),TODO 是未做功能(不阻塞运行),危险度不同。CI 可统计未关闭标记数量趋势,只增不减说明在堆积,该集中清理。
- **别当文档**:标记是状态标签,不是解释代码的注释。解释代码该靠命名 / 结构 / docstring(见 `code-guidelines` 及语言专项 `python-guidelines` / `cpp-guidelines`),别用 `NOTE` 顶替该写的 docstring。
