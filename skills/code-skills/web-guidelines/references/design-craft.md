# 设计与文案准则(design-craft)

> **来源**:吸收自 [anthropics/skills](https://github.com/anthropics/skills) 的 `frontend-design` 与 [leonxlnx/taste-skill](https://github.com/leonxlnx/taste-skill) 的工程纪律(设计读法、一致性锁、动效有动机、假数字禁)。两者原文面向品牌落地页/作品集;本参考只取对**应用界面 / 报告**同样成立的部分,按 SaaS 平台 + 报告渲染场景改写。品牌营销专属内容(hero 叙事、品牌签名)与落地页布局细则不在此列。
>
> **定位**:回答「怎么让产物**逻辑清晰、表现力强**,不像模板」——① 应用型 UI 与 ② 报告渲染共享的审美与文案层。组件骨架看 `app-ui-design.md`,报告形态看 `report-rendering.md`,动手前先过本文。

## 0. 先钉住主题,声明设计读法

报告的主题就是它的**数据与结论**;SaaS 界面的主题是它要**完成的任务**。动手前一句话说清:这份产物给谁看、单一职责是什么。设计选择从主题本身长出来——领域的数据形态、术语、单位、异常的样子——不从模板里来。主题自己的世界才是独特选择的来源。

钉住后,生成前先给一句**设计读法**声明:「读作:给 <受众> 的 <产物类型>,<基调>,用 <基底>」。声明让取向显式、用户可当场纠正;能自信推断就直接声明并继续,只有读法真的分叉时才问——**且只问一个问题**(如「更克制还是更有实验性?」),不搞问题倾倒。

## 1. 设计原则

- **开篇即论点**:报告的执行摘要 / 关键结论前置,别让读者翻三屏才看到重点;应用的首屏即工作区,别拿欢迎横幅占位。
- **字体三角色**:展示(标题,克制用)/ 正文 / **数据字**(等宽数字 `tabular-nums`,表格与指标必用)。层级靠字号/字重/字距刻意设定,不是顺手默认;让字体处理本身成为值得记住的部分,而不是内容的中立容器。
- **结构即信息**:编号、眉标、分隔线、标签要**编码内容的真实关系**,不是装饰。只有内容真是序列(流程、时间线、顺序携带读者需要的信息)才用 01/02/03;报告章节号同理。加结构手段前先问它承载了什么信息。
- **动效有动机**:每个动效要能一句话说清它传达什么——层级、反馈、状态转移;「看着酷」不是理由,说不清就删。一次编排好的时刻胜过散落特效;应用里动效只用于反馈与引导注意,报告里至多用于图表揭示。多余动效强化「AI 生成感」,少即是多。
- **复杂度匹配愿景**:信息密集的界面/报告,优雅 = 把密度执行到位(间距、字号、对齐的精确),不是堆装饰;极简方向同样靠细节精确撑起来。

## 2. 校准:避开默认样式簇

AI 生成的设计扎堆几种外观。落地页的三种(暖米色+衬线+赤陶橙、近黑+酸绿、报纸式)之外,**应用与报告有自己的默认簇**:

- **SaaS 默认脸**:蓝紫渐变 + 圆角卡片阵 + 顶部一排 stat 卡 + 系统默认字体。
- **报告默认脸**:居中大标题 + 渐变横幅 + 三列等宽卡片 + emoji 当图标。

这些本身不违法,但它们是**默认值不是选择**——与主题无关地出现就是模板。用户定死了方向就严格照做;留了自由轴,别把自由花在默认上。

## 2b. 一致性锁

模板感不只来自「长得像别人」,也来自「自己内部打架」。定稿前逐项锁死:

- **配色锁**:强调色全产物唯一(一个页面/一份报告一个 accent)。暖灰基底不会在第 7 节突然冒出蓝 CTA;状态色语义全站一致(与 app-ui token 同源)。
- **形状锁**:圆角尺度全产物一套(全直角 / 全软角 12–16px / 交互元素全胶囊),要么统一要么有明文规则;圆按钮配方卡片就是破的。
- **字体锁**:字体角色(展示/正文/数据)定了就不换;数字一律 `tabular-nums`。
- **主题锁**:报告默认单主题;应用双主题从第一天设计(见 app-ui §2),但任一时刻全站一个主题,不出现中途反色的区段。

## 3. 两遍法

**第一遍——规划**(动手前):出一份紧凑设计计划,四件套:

- **配色**:4–6 个具名 hex(应用沿用 app-ui 的中性色+状态色框架)。
- **字体**:2+ 角色(展示 / 正文 / 数据字)。
- **布局**:一句话概念 + ASCII 线框对比。
- **签名元素**:这份产物被记住的**那一个**东西——报告里可能是一张核心图表,应用里可能是一种独到的导航方式。

**第二遍——审查计划再构建**:对着主题审一遍——任何一部分若「换个项目也会长这样」就改掉,并说明改了什么、为什么。确认计划的相对独特性后才写码,每个颜色/字体决策从计划推导。

写码注意 CSS 选择器优先级互相抵消(`.section` 与 `.cta` 抢 padding/margin 是常见事故)。规划与迭代尽量在思考里完成,有把握再给用户看。

## 4. 克制与自评

- **大胆只花一处**:签名元素是唯一被记住的东西,周围保持安静与纪律,砍掉一切不为主题服务的装饰。不冒险本身也是风险。
- **质量底线不声张**:响应式、键盘焦点可见、尊重 reduced-motion(动效强度越高越必须,滚动劫持/无限循环/视差在 reduced-motion 下塌缩为静态);报告额外做打印预览(常被转 PDF 存档)。动画只动 `transform` 和 `opacity`,不动 top/left/width/height。
- **边做边自评**:能截图就截图自审,一图顶一千 token。Chanel 的建议:出门前照镜子,摘掉一件配饰。

## 5. 文案即设计材料

界面/报告里的字只有一个目的:**让人更容易理解,因此更容易使用**。

- **从用户那一侧命名**:人管理的是「通知」,不是「webhook 配置」。具体永远好过机灵。
- **主动语态 + 全程同名**:「保存更改」不是「提交」;按钮叫「发布」,toast 就说「已发布」。词汇是导航的路标,一致性让人学会在系统里走动。同一意图全产物只用一个词(「导出」「下载」「另存为」别混用)。
- **失败与空态是方向不是情绪**:说清哪里错、怎么修;错误不道歉、不含糊;空屏是行动的邀请(呼应 app-ui 的三态)。
- **各司其职**:标签就做标签、示例就做示例,没有悄悄身兼数职的元素。
- **文案自审**:交付前重读全部可见字符串,标记语法破碎、指代不明、强行比喻、「AI 味的机灵」——每条改写成朴素且功能性的话。机灵的废话不如朴素的实话。
- **数字不许造假**:精确数字(92%、4.1×、5.8ms)要么来自真实数据,要么明确标注 mock/示例;不许用编造的精确感充门面。
