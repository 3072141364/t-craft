# 报告渲染(report-rendering)

> **场景**:把数据/分析结果渲染成**报告页**——测试报告、评估报告、数据分析、审查结果、周报汇总。报告是「读的」不是「用的」:一次产出、被人阅读、可能导出存档,交互密度远低于 SaaS 界面,信息密度与可读性要求更高。
>
> **定位**:web-guidelines 的独立产出形态之一。骨架与 token 沿用 `app-ui-design.md`,审美与文案过 `design-craft.md`,本文管报告特有的结构、图表与导出。

## 报告与 SaaS 界面的差别

| 维度 | SaaS 界面(app-ui) | 报告(report) |
|------|--------------------|----------------|
| 目标 | 高效完成任务 | 高效传递结论 |
| 交互 | 表格/表单/快捷键,天天用 | 几乎只读,一次产出 |
| 首屏 | 工作区 | 结论(执行摘要/关键指标) |
| 生命周期 | 持续迭代 | 生成→阅读→存档/转发 |
| 特有约束 | 三态、暗色 | 打印/导出友好 |

## 1. 结构:结论金字塔

- **结论前置**:执行摘要 / TL;DR 放最顶——读者 10 秒内知道「好不好、要不要行动」。别把结论埋在最后一章。
- **逐层下钻**:结论 → 关键证据(指标/图表)→ 明细(表格/附录)。读者随时可以停,停在哪一层都不亏。
- **章节编号承载真实序列**:报告天然是序列,编号成立;但同层的并列要点(无顺序语义)别硬编号,用眉标或分组。
- **锚点导航**:长报告顶部给目录/锚点,侧栏显示当前位置。

## 2. 数据呈现

- **指标卡慎用**:顶部 3–5 个关键指标可以,一排十几个 stat 卡是「报告默认脸」。每个指标给**参照系**(环比/阈值/目标),裸数字没有意义。
- **图表选型跟结论走**:趋势→折线;对比→条形;构成→堆叠/占比;分布→直方图/箱线。图表标题写结论(「失败率周环比 +12%」),不写内容描述(「失败率趋势图」)。
- **表格可扫读**:数字右对齐 + `tabular-nums`,异常值高亮(状态色),长表冻结表头,明细超长折叠/分页。
- **好/坏/需关注用状态色**,全报告语义一致(与 app-ui 的状态色 token 同源)。

## 3. 视觉与文案

- **打印/导出是常态**:默认按「会被转 PDF」设计——避免依赖屏幕宽度的横向布局,打印断点(`@media print`)处理分页、去交互元素、背景色用 `print-color-adjust` 保留关键高亮。
- **暗色可选**:报告通常单主题(亮色)即可,不追求双主题;屏幕阅读为主且周期长的才考虑。
- **文案过 design-craft §5**:结论写清楚「发生了什么、影响是什么、建议做什么」;错误不粉饰;空数据区块说明原因而不是留白。

## 4. 生成流程

1. **先定结论**:报告的数据出来先提炼 3–5 条结论,报告围绕结论组织——不是数据的无序罗列。
2. **两遍法过 design-craft**:规划(token/布局/签名元素——报告的签名常是核心图表的呈现方式)→ 审计划避默认脸 → 生成。
3. **技术选型按场景**:一次性 HTML 报告直接写(内联 CSS,无外部依赖,便于转发);平台内嵌报告页走项目组件库;需要 PDF 就从打印样式导出,不另做一套。
4. **交付后自评**:截图过一遍——10 秒测试(能否快速抓到结论)、打印预览、移动端窄屏。
