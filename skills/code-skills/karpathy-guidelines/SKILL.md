# 编码行为准则

减少 LLM 编码常见错误的行为准则,源自 [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876)。

**权衡**:这些准则偏向谨慎而非速度。对琐碎任务,自行判断。

## 项目约束发现

本准则的「原则」是通用的;但落到具体项目时,要把原则接到该项目的约束上(保护分支、版本真源、模块布局、格式化命令、提交流程等)。这些**不在本 skill 硬编码**,而是:

1. **读项目 `CLAUDE.md`**:提取本项目定稿下的约束(分支策略、版本真源、make/格式化命令、目录约定、提交规范等)。若 CLAUDE.md 引用了规范文档(如 `docs/development.md`),一并读。
2. **以文件实际内容为准**,不凭记忆。

下面各节的原则,结合从 CLAUDE.md 读到的项目约束来执行。

## 1. 先思考再写码

**不要假设。不要掩饰困惑。显式暴露权衡。**

实现前:

- 显式陈述假设,不确定就问。
- 若存在多种解读,全部呈现 -- 不要默默替用户选一个。
- 若有更简单的方案,说出来,该 push back 就 push back。
- 若某处不清楚,停下,指出困惑点,提问。

项目约束(从 CLAUDE.md 读):改代码前确认当前分支是否允许直接改(如受保护分支禁直推,先切工作分支);涉及版本/发版/分支策略时以项目版本真源与规范文档为准。

## 2. 简洁优先

**解决问题的最小代码。不做投机性的事。**

- 不写要求之外的功能。
- 单次使用的代码不抽象。
- 不写未被要求的"灵活性""可配置性"。
- 不为不可能发生的场景写错误处理。
- 若写了 200 行而本可 50 行,重写。

自问:"资深工程师会说这过度复杂吗?"若是,简化。

项目约束:新增模块走项目约定的源码目录(从 CLAUDE.md 读,如 `src/<pkg>/`),职责单一;公共配置集中在项目配置文件,不各处重复。

## 3. 外科手术式修改

**只动该动的。只清理自己制造的混乱。**

- 不"顺手优化"相邻的代码、注释、格式。
- 不重构没坏的东西。
- 匹配既有风格,即使你想用别的方式。
- 发现无关的死代码,**指出来**,不要删。
- 移除**你的改动**导致无用的 import/变量/函数;不移除既有死代码,除非被要求。

检验标准:每一行改动都能直接追溯到用户的请求。

项目约束:匹配既有代码风格(从 CLAUDE.md 读项目的 formatter 配置与格式化命令,提交前跑);版本真源只在该动时递增(按 SemVer),不随意改。

## 4. 目标驱动执行

**定义成功标准。循环直至验证。**

把任务转化为可验证的目标:

- "加校验" -> "为非法输入写测试,再让测试通过"
- "修 bug" -> "写一个能复现的测试,再让它通过"
- "重构 X" -> "确保改前改后测试都通过"

多步任务,先陈述简要计划:

```
1. [步骤] -> 验证:[检查]
2. [步骤] -> 验证:[检查]
```

强的成功标准让你能独立循环推进;弱的标准("让它能跑")需要不断澄清。

项目约束:提交前验证项以 CLAUDE.md 为准(格式化、lint、test、CHANGELOG 更新、版本号是否递增等)。

## 5. 提交即规范

**改完代码后,提交走 skill,不手动 git。**

- 提交代码走 `git-flow` skill(本 plugin 内):格式化 -> CHANGELOG -> 版本号 -> commit -> push(确认),不手动 `git commit`。
- 受保护分支禁直推,先切工作分支。
- commit 信息行首带与 type 对应的 gitmoji(向 `emoji-helper` skill 查询)。
- CHANGELOG 与 commit 的 emoji 呼应,语义一致。

## 附:与内置准则的关系

Claude 内置已有大量类似行为准则,本 skill 的增量在于:

- **把通用原则落到项目约束**:结合项目 CLAUDE.md 的具体约束(路径、命令、规范条款),使原则可执行而非停留于原则层面。
- **团队一致认知**:入库后,所有协作者(含不同 AI 助手)看到的准则一致,不依赖内置版本的黑盒差异。
