触发 code-guidelines 附属文档 **brainstorm.md** 的需求深挖流程。这是研发流程阶段①(方案设计前)的入口。

## 参数

- 无参数:对当前对话中已提到的需求深挖(若对话里还没有明确需求,先问用户"要深挖什么")。
- `<一句话需求描述>`(如 `/tcraft-brainstorm 给导出加 PDF 格式`):对该需求深挖。

## 执行

读 code-guidelines 的附属文档 `brainstorm.md`(路径 `../code-guidelines/references/brainstorm.md`)。按其完整流程走:

1. **前置:发现项目约定**——读项目 CLAUDE.md、探测标准位置、读可选描述文件,以文件实际内容为准。
2. **探索上下文先**——读相关代码 / 文档 / 近期 commit;代码能答的不问用户。
3. **开问题队列**——列出深挖维度(真实意图 / 约束 / 边界 / 风险 / 验收 / 旧方案),让用户看到全貌与进度。
4. **弹性一次一问**——默认每条消息一个问题 + 推荐答案;遇简单确认或紧密相关的分支问题允许 2-3 个合并;YAGNI,剔除不必要的功能假设。
5. **范围检查**——若需求含多个独立子系统,先提示拆解,只深挖第一项。
6. **联动查旧方案**——用 obsidian-kb 模块二(query.md,3-tier 读)查 vault 相关旧方案、踩坑、决策卡。
7. **追问工具(按需)**——遇「症状 vs 根因」卡点走 5-Whys 子流程;遇「假设存疑 / 方案是否最优」卡点走 first-principles 子流程。不强制每次走。
8. **产出需求要点**——HARD-GATE:用户确认前不进实现、不写方案文件。确认后在对话内呈现需求要点(目标 / 约束 / 验收标准 / 相关旧方案 / 范围外),不落盘(落盘是阶段② obsidian-kb 的职责)。
9. **交接阶段②**——提示用户用 obsidian-kb 把方案写到 vault。

## 约定

- **不擅自进实现**:深挖阶段只产出需求要点,不写代码、不写方案文件。
- **每步确认**:产出需求要点前展示给用户确认。
- **以项目文件实际内容为准**:项目约定从 CLAUDE.md / 规范文档读,不凭记忆。
- **失败要明确**:读不到的关键约定,停止并提示,不凭空假设。
