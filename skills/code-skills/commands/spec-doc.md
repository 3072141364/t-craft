触发 **spec-doc** skill 的方案文档生成流程。这是研发流程阶段②(方案设计)的入口。

## 参数

- 无参数:对当前对话中已对齐的需求(或 brainstorm 产出的需求要点)落方案文档。若对话里还没有需求,先问用户"要落什么方案"。
- `<一句话需求>`(如 `/spec-doc 给导出加 PDF 格式`):对该需求落方案文档(若需求含糊,提示先走 brainstorm 深挖)。
- `eval`:触发评估测试文档形态(**后补,未实现**,会提示"评估测试文档段待实现")。

## 执行

调用 `spec-doc` skill(同 plugin,code-skills)。按其完整流程走:

1. **前置:发现项目约定**——读项目 CLAUDE.md、探测标准位置、读可选描述文件、读 obsidian-kb 的 vault 约定(方案卡片路径/模板),以文件实际内容为准。
2. **取输入**——读 brainstorm 产出的需求要点(若上游走过);否则从用户给的需求描述取。不重新采访。
3. **探索代码库**(若未探索)——读相关代码/CLAUDE.md,用项目领域词。
4. **勾测试 seam**——草拟测试切入点(优先既有、最高 seam),与用户确认。
5. **起草方案文档**——按骨架,按读者分章:
   - **用户读**:需求背景 / 方案设计(含方案设计图,按需联动 fireworks-tech-graph / 方案优缺点)/ 项目收益 / 行动清单 / 验收标准
   - **AI 读**:AI 须知(范围外 / 代码变更清单 / 测试决策 / 其他实现约束)
   - 候选方案/权衡是头脑风暴过程,不进文档;只记最终方案 + 优缺点。
6. **落盘**——调 obsidian-kb 写到 `项目/<名>/方案/<方案名>.md`,`card_type:方案`。代码仓库留指针(`> 方案见 Obsidian: [[方案名]]`)。
7. **自审**——扫占位/矛盾/歧义/范围,修完再交付。
8. **用户审**——交付后请用户审 spec 文件,要改则改 + 重跑自审。

## 约定

- **HARD-GATE**:方案文档用户确认前不进实现、不写代码。
- **不重新采访**:综合已对齐内容,不再问一轮需求问题(需求含糊则提示先走 brainstorm)。
- **落盘走 obsidian-kb**:不自行写文件到 vault,调 obsidian-kb 落盘。
- **按读者分章**:用户读主体 + AI 须知,不混杂。
- **以项目文件实际内容为准**:项目约定从 CLAUDE.md / 规范文档读,不凭记忆。
